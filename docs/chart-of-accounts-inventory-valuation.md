# شجرة الحسابات وقيمة المخزون بالتكلفة
تاريخ التنفيذ: 2026-11-02. PHP 8.5.12، Laravel 13.35، MySQL محلي.

## الموجود والتغيير
يوجد دفتر موحد بالفعل: financial_accounts وjournal_entries وjournal_lines، مع قيد لكل مصدر/حدث، ومعاملات وتدقيق وترحيل مزدوج. المشتريات تثبت المخزون وذمم الموردين، والبيع يثبت الإيراد والتكلفة وخروج المخزون، والمرتجعات تعكس الأثر المناسب. سندات القبض والسداد والتحويل منفصلة عن الإيراد والمصروف. التوصيل يستخدم إيرادًا مستقلًا وعهدة للمزوّد، وأجرته مصروف مستقل.

لم تُبنَ محاسبة موازية. ظلت الأكواد والأنواع الأصلية cash/bank/wallet/system، والعلاقات والمبالغ والقيود كما هي. الجديد:
- شجرة في نفس الحسابات، مع أب اختياري، وتصنيف محاسبي مستقل عن نوع الحساب التشغيلي، وطبيعة رصيد، وتمييز التجميعي والتفصيلي والحساب المحمي.
- المجموعات الخمس جذور عرض افتراضية فوق الحسابات، ولا تنشئ صفوفًا أو قيودًا عند فتح الصفحة.
- إضافة رئيسي/فرعي، بحث بالرمز والاسم، طي/فتح، عرض الأرصدة وحركات الحساب، وتعديل الاسم والحالة وفق الضوابط.
- بطاقة Dashboard وتقرير مطابقة المخزون والدفتر، ضمن الفروع المسموحة.
- لا إعادة تقسيم تاريخية للمصروفات المجمعة أو حركات المالك. إضافة حساب جديد لا تعيد توجيه المستندات إليه تلقائيًا. يمكن تعريف أصل ثابت أو حساب فرعي حسب الحاجة؛ لا ضرائب أو رواتب أو أرصدة افتراضية تلقائية.

## الصلاحيات والضوابط
العرض في /finance/chart وحركات الحساب يتطلب finance.view وsales.view_cost. الإدارة تضيف sales.manage_accounts الحالية؛ الحساب العام يحتاج sales.all_branches. لم تُضف صلاحيات جديدة ولم تُحدَّث أدوار app_store. الكاشير الافتراضي ممنوع من الشجرة وتقييم التكلفة، ويظل عمله الحالي متاحًا.

التجميعي لا يستقبل قيودًا؛ يجب أن يكون الأب فعالًا وتجميعيًا من المجموعة المناسبة ونطاق فرع متوافق. تُمنع الحلقات وتكرارات الأكواد داخل فضاء الأكواد العالمي الموجود أصلًا. العمليات تقفل العداد المشترك وسجل الحساب والأب، وتُدقّق قبل/بعد مع المستخدم والوقت والسبب داخل معاملة واحدة.

الحسابات الموجودة وحسابات النظام الجديدة محمية. لا تغيير رمزها أو تصنيفها أو طبيعتها أو فرعها أو نوعها أو تحويلها لتجميعية أو تعطيلها من هذه الشاشة. يسمح بتحسين اسمها مع التدقيق. الحسابات المخصصة التي لها قيود أو أبناء لا يُغير هيكلها أو تُعطل. الحساب المخصص غير المستخدم يمكن تعطيله وإعادة تفعيله. لا مسار حذف، والنموذج يرفض الحذف أيضًا.

أضيف حاجز في PostJournalAction قبل إنشاء القيد للتحقق من حساب تفصيلي فعال ضمن الفرع، دون تغيير الحسابات أو المبالغ التي تختارها المستندات. إعادة القيود المقبولة تحتفظ بمسارها القائم، والعكس التاريخي يحتفظ بدعمه. يوجد أيضًا حاجز MySQL يمنع إدراج journal_lines على التجميعي، وحاجز لحماية بنية الحساب النظامي/التاريخي. لم يتغير فحص توازن المدين والدائن أو مفتاح منع تكرار الحدث.

## تقييم المخزون
StockLedger يستخدم القيمة الصحيحة value_minor والمتوسط المرجح؛ متوسط العرض average_cost محفوظ للتيسير وليس مصدر ضرب الإجمالي. البطاقة تجمع القيم المعتمدة في SQL، وتشمل المتاح المملوك بما فيه المحجوز، وقيمة قيد الفحص بصورة منفصلة. التالف لا يُمنح قيمة جديدة مخمنة. العملة الحالية للمشروع ₪، والحساب بوحداتها الصغرى وMoney، دون Float أو جمع كل الأصناف في PHP.

تظهر القيمة غير مكتملة عند قيمة مجهولة أو رصيد غير صالح، مع عدد المشكلات. تُفحص الكميات والقيم مقابل حركات المتاح وقيد الفحص. الفرق مع حسابي inventory وquarantine في الدفتر يظهر منفصلًا، دون تصفير أو قيد آلي. حركات الدفتر مقيدة بفرع القيد، وليس بمجرد branch_id للحساب النظامي العام.

البطاقة تتطلب inventory.view وsales.view_cost. من لا يملك finance.view لا تُجرى له قراءة رصيد الدفتر ولا يصل إلى بيانات View أي مبلغ دفتر أو فرق؛ تبقى قيمة المخزون المسموحة فقط. تقرير المطابقة يتطلب الصلاحيات الثلاث.

[IAS 2 الرسمي](https://www.ifrs.org/issued-standards/list-of-standards/ias-2-inventories/) يسمح بالمتوسط المرجح للأصناف القابلة للتبادل، ويشترط النظر إلى الأقل من التكلفة وصافي القيمة القابلة للتحقق. هذه المهمة تحافظ على التكلفة والسياسة القائمة؛ لا تضيف تقدير NRV تلقائيًا ولا تثبت امتثال IFRS أو قانون ضريبي كاملًا.

## الفحص الحالي للقراءة فقط
لا اعتماد على الرقم التاريخي 250 أو 3,150. الفحص عند بدء المهمة:
- 19 حسابًا قائمًا، جميعها قابلة للتصنيف دون إعادة ترقيم.
- 9 أرصدة مخزون، 315 قطعة.
- القيمة المعتمدة بالمخزون 6,090.00، قيد الفحص صفر، دون قيم مجهولة.
- رصيد حساب المخزون 1,500.00؛ الفرق 4,590.00.
- كميات وقيم المخزون تطابق سجل الحركات في الفحص الحالي.

الدليل المستندي:
| المصدر | قيمة المخزون | الدليل المالي |
|---|---:|---|
| OS-000001 | 250.00 | ترحيل أول المدة غير مثبت |
| OS-000002 | 2,900.00 | ترحيل أول المدة غير مثبت |
| OS-000003 | 1,440.00 | ترحيل أول المدة غير مثبت |
| PI-000001 | 1,500.00 | ترحيل شراء موجود |

مجموع مستندات أول المدة أعلاه يطابق الفرق 4,590.00. هذا تفسير للدليل الحالي، وليس إذنًا بترحيلها أو إغلاق الإعداد. تقرير المطابقة يعرض كل رصيد ومصادره، مع رابط إلى مراجعة المخزون لمن يملك صلاحيتها. لم تُعدّل سياسة التكلفة أو قيود العميل.

## الترحيل وحالة app_store
الجديد:
database/migrations/2026_11_02_181118_add_chart_hierarchy_to_financial_accounts.php

يضيف parent_id مع FK وفهرس، account_group مع فهرس، normal_balance، is_posting، is_protected إلى financial_accounts، ويصنف الحسابات القائمة دون تغيير أي عمود قديم أو مبلغ. الرمز الفريد الموجود أصلًا يبقى كما هو. لا حسابات أو أرصدة افتراضية. يتوقف قبل DDL إذا وجد حسابًا لا يملك تصنيفًا معروفًا، بدل تخمينه.

اختُبر تطبيقه بآلية Laravel على appstore_golive_20261031_tests وعلى قاعدة التدقيق المعزولة appstore_financial_audit_a1db3a4e547bdba0، ثم طُبق الترحيل المحدد وحده على app_store المحلية بعد موافقة المستخدم الصريحة. لا migrate:fresh أو db:wipe.

اكتمل التحديث المحلي وأصبحت إضافة الحسابات وتعديلها متاحة للصلاحيات القائمة. فُحص توليد /finance/chart و/dashboard و/finance/inventory-reconciliation من اتصال app_store نفسه عبر HTTP Kernel بجلسة ذاكرة واتصال SQL مقيد بالقراءة: الصفحات الثلاث 200 ونموذج الإضافة مفعّل للمالك. لم يُنشأ حساب تجريبي على قاعدة المحل. down يرفض إسقاط حالة الشجرة وحواجز المحاسبة تلقائيًا؛ أي تراجع يحتاج خطة معتمدة.

قبل التنفيذ أُعيد إثبات local/mysql/127.0.0.1:3306/app_store وPHP 8.5.12، وعدم وجود Schema جزئي، وأن الترحيل الوحيد المعلق هو المحدد أعلاه. تحقق التصنيف للحسابات الـ19 وصلاحيات المالك الحالية دون تحديث أدواره. بعد التنفيذ: 65 Trigger، منها الحواجز الـ63 الأصلية محفوظة وحاجزا الشجرة الجديدان، مع FK الأب والفهارس. التحديث يولد 38 إشارة accounts في mobile_sync_changes عبر حواجز المزامنة القائمة؛ عُدّت وفُحصت كأثر متوقع للتصنيف، وليست قيودًا مالية.

## حماية البيانات والتغييرات المتزامنة
المرحلة الأولى والفحوص قبل وبعد التنفيذ استخدمت قراءة محمية بـ SET SESSION TRANSACTION READ ONLY. بعد موافقة المستخدم طُبق الترحيل المحدد فقط على app_store؛ اختبارات الحفظ والعمليات المالية بقيت على القواعد المعزولة.

مقارنة مرحلة التطوير الأولى لم تطابق جميع الجداول: تغيرت audit_events وexpense_payments وexpenses وjournal_entries وjournal_lines وproduct_code_counters أثناء فترة العمل، إضافة إلى cache وsessions. سجل التدقيق أظهر إنشاء/اعتماد المصروف 2 وسداده، ثم اعتماد المصروف 1 وسداد جزء منه، بحساب المستخدم 2. أكد المستخدم أنه كان يجرب المصروفات والسداد؛ احتُفظ بهذه العمليات كاملة دون حذف أو تراجع.

أُخذت لقطة جديدة مباشرة قبل الترحيل المعتمد، تشمل الجداول الـ74 والعمليات التي جربها المستخدم. المقارنة بعده أثبتت تطابق كل الأعمدة القديمة للحسابات وكل بيانات الأعمال، بما فيها قيود المصروفات وسدادها. تغيّرت فقط migrations وmobile_sync_changes وmobile_sync_clock، إضافة إلى حقول تصنيف الحسابات الجديدة. لم تنشأ حسابات أو قيود، وبقيت قيمة المخزون 6,090.00 ورصيد حسابه 1,500.00 والفرق 4,590.00 وحالة الإعداد كما هي.

الأدلة الأولى: storage/app/reports/chart-before.json وchart-current-reconciliation.json وchart-preservation.json. أدلة التطبيق المعتمد: chart-local-upgrade-before.json وchart-local-upgrade-after.json وchart-local-upgrade-pages.json. لا كلمات مرور أو رموز حسابات دخول في التقرير.
