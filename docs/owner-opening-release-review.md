## الموانع بحسب الأولوية

### 1. خلل محاسبي مثبت في تصحيح البضاعة بعد الاعتماد

`app/Actions/Inventory/Setup/CorrectInventoryAction.php:207` يشترط تفعيل `sales_controls.activated_at` لتسجيل قيد `opening_correction`، رغم أن الاعتماد الجديد يسجل القيد الافتتاحي أثناء إغلاق البيع. مسار التعديل يغيّر كمية وقيمة المخزون وسطوره وحركته، ثم يتخطى قيد الفرق عندما يكون البيع مغلقًا. شرط القيد نفسه موجود في مسار الحذف المشترك؛ الاختبار المنفذ أثبت التعديل تحديدًا، ولم ينفذ حذفًا على بيانات العميل.

الإثبات على MySQL المعزول:

| المرحلة | قيمة المخزون | رصيد حساب المخزون |
|---|---:|---:|
| اعتماد 3 وحدات × 12.50 والبيع مغلق | 37.50 | 37.50 |
| تصحيح الكمية إلى 4 وحدات عبر HTTP | 50.00 | 37.50 |

الفرق الجديد 12.50، وليس فرقًا تاريخيًا من بيانات المحل. نجح طلب التعديل HTTP 200، وفشل اختبار مطابقة المخزون والدفتر. المسار المتأثر `PUT /inventory/{inventory}`؛ Inventory API يستدعي `UpsertInventoryAction` الذي يمر بخدمة التصحيح نفسها. لا يوجد مسار اعتماد جديد مستقل هنا، لكن التصحيح اللاحق ينقض المطابقة التي يحققها الاعتماد.

الإصلاح المقترح: ربط قيد فرق التصحيح بوجود الأثر المالي المعتمد للمصدر، مستقلًا عن فتح البيع، أو رفض التصحيح إذا لم يكن المصدر مرحّلًا. الحفاظ على Transaction والأقفال وفحص الإصدار؛ وعدم إنشاء قيد افتتاحي تاريخي تلقائيًا. يلزم اختبار تعديل الكمية والتكلفة والحذف، والتراجع عند فشل قيد الفرق، والتكرار والتزامن، في حالتي البيع المغلق والمفتوح. لم أطبق هذا التغيير المحاسبي في جلسة المراجعة.

### 2. اختبارات التصحيح القديمة غير متوافقة مع مسار الاعتماد الجديد

المجموعة `InventorySetupTest` أظهرت 23 خطأ تجهيز: تستدعي `PostOpeningStockAction::execute` دون `actorId` ثم تتوقع وجود Inventory. المسار الجديد يحفظ مسودة، ويفشل إيجاد مستخدم الاعتماد، فيبقيها مسودة؛ لذلك تفشل `Inventory::firstOrFail` قبل اختبار التصحيح أصلًا. هذا تشخيص لتجهيز الاختبارات، وليس إثباتًا أن الـController الرسمي يرسل مستخدمًا مفقودًا؛ Controller الويب وFlutter يمرران المستخدم، وكذلك Seeder العرض الذي روجع للقراءة فقط.

المطلوب تحديث هذه العينات لتمرير مستخدم مخوّل صراحة، ثم مراجعة توقعات القيود وإعادة المجموعة كاملة. لا يُعالج ذلك بإلغاء المصادقة أو السماح باعتماد بلا مستخدم. لم أعدّل هذه الاختبارات القديمة أو أتجاوزها لإخفاء الفشل.

## ما ثبت سلامته ضمن النطاق المفحوص

- روجعت التعديلات المتتبعة وملفات الكود والاختبارات الجديدة غير المتتبعة. تغييرات المهمة تخص الاعتماد والجاهزية والصلاحيات المشتقة والتصدير واختباراتها؛ اختبارات الصور السابقة عمل مستقل محفوظ وليست تعديلًا جديدًا لهذه المهمة. `HomeRouteTest.php` لا يحمل فرقًا نصيًا. بصمتا الملفين تطابقان نهاية الجلسة السابقة.
- لا تغييرات في `config` أو Seeders أو Migrations أو `composer.json/lock` ضمن الفرق الحالي. لم يُشغّل Seeder أو Migration أو استيراد، ولم يتصل العمل بقاعدة العميل أو Testing/Production.
- `ManageOpeningDraftAction::approve` يستخدم `OperationContext::run` مع Transaction وقفل مشترك، ثم قفل المستند وفحص حالته وإصداره. إدخال المخزون وحركته والقيد وحالة الاعتماد والتدقيق ضمن Transaction واحدة. حفظ المسودة مرحلة مستقلة كي تبقى عند فشل الاعتماد؛ المسودة لا تدخل المخزون.
- القيد مدين `inventory` ودائن `opening_equity`، دون ذمة مورد. `PostJournalAction` يرفض الترحيل خارج Transaction والقيد غير المتوازن. توجد حماية المصدر/الحدث وفهرس `journal_source_event_unique` في تعريف Schema، واختبار تزامن فعلي ناجح يمنع تكرار الكمية والقيد.
- الاعتماد المباشر واعتماد المسودة و`opening_stock.create` في Flutter تصل إلى المسار المشترك. لم يظهر مسار اعتماد منتج جديد آخر يتجاوز هذا القيد ضمن الخدمات والمسارات المراجعة. مسار الاستيراد القديم خارج التشغيل الرسمي؛ لم يُشغّل أو يُختبر هنا.
- `ManageFinancialAccountsAction::provision` يستخدم `firstOrCreate` لإنشاء الحسابات النظامية الناقصة فقط. لا يسجل قيودًا أو أرصدة ولا يحدّث الأدوار والصلاحيات، ولا يعيد تفعيل حساب موجود. الزيادة الطبيعية في رصيد المخزون عند اعتماد بضاعة جديدة مصدرها القيد المعتمد، وليست أثر تجهيز الحسابات.
- المستند المعتمد عند إعادة الطلب لا يستقبل مخزونه أو قيده مجددًا. المستند التاريخي بلا قيد يبقى للمراجعة في المسار المالي المنفصل؛ لا ترحيل تاريخي أو تشغيل بيع تلقائيًا في هذه التعديلات.

## Excel وتوافق البيئة

راجعت بنية XLSX والملفات المؤقتة وصلاحيات التصدير ونطاق الفرع والفلاتر. الاختبارات تثبت جميع الصفوف، المبالغ الرقمية، SKU النصي، الخلايا الفارغة للقيم المجهولة، منع Formula، وبقاء JSON وعدم تعديل بيانات الأعمال عند التنزيل.

- المثبت محليًا: Laravel 13.35.0، PHP 8.5.12 للاختبارات الأساسية، وPHP 8.3.16 في PATH. `composer show --direct` وفحص `composer check-platform-reqs --no-dev` على PHP 8.3 نجحا وفق الحزم المثبتة. لا تغيير Dependencies.
- اختبارات Excel الأربعة نجحت أيضًا فعليًا على PHP 8.3.16. لا يعني هذا إعادة حزمة المشروع كلها على الإصدارين.
- يلزم `ZipArchive` من امتداد ZIP و`XMLWriter`، و`mbstring`، ومجلد مؤقت قابل للكتابة ومساحة مناسبة. ZIP معطل في إعداد PHP 8.5 المحلي الافتراضي؛ استُخدم `-d extension=zip` للاختبارات فقط. PHP 8.3 المحلي يفعّل ZIP وXMLWriter.
- يجب فحص هذه المتطلبات في **PHP-FPM الذي يخدم الموقع وفي CLI**؛ Composer platform check وحده لا يضمن ZIP لأنه غير مصرح به كمتطلب Composer لهذا الكاتب. لا تُنشئ صفحة `phpinfo` عامة للتحقق.
- لم أتصل بالسيرفر؛ إصدار PHP-FPM وامتداداته وصلاحيات Linux غير متحققة. لم يُفتح الملف في Microsoft Excel/LibreOffice فعلي، ولم يُنفذ اختبار متصفح جديد في هذه المراجعة.

## خطة النشر المقترحة — لم تنفذ

1. **قبل Testing:** إصلاح المانع المحاسبي، وتحديث عينات التصحيح وإعادة اختبارات التعديل والحذف والتراجع والتزامن والمطابقة. لا تعويض أو ترحيل تاريخي تلقائي. إعادة الحزمة المرتبطة وإرفاق نتائج ناجحة قبل اعتماد نسخة مرشحة.
2. **تحضير Testing:** نسخة مستقلة وقاعدة وصور اختبار مستقلة، وتوثيق إعدادات `.env` والتعديلات اليدوية ونسخة الإصدار الحالي. الاحتفاظ بنسخة احتياطية حديثة واختبار استعادتها في وجهة معزولة. مراجعة PHP-FPM/CLI وZIP/XMLWriter ومتطلبات Composer. هذه التغييرات لا تحتاج Migration أو Seeder أو تحديث صلاحيات.
3. **تجهيز الإصدار:** إدراج الملفات الجديدة غير المتتبعة ضمن الحزمة بعد المراجعة، دون `.env` أو ملفات الرموز أو Credentials أو استبدال `storage` وصور العميل. استعمال `composer.lock`؛ تجنب `composer update` و`composer run setup` وأوامر الاستيراد والنشر الشاملة التي قد تشغّل ترحيلات. معالجة Cache/OPcache والعمال وفق إصدار PHP المحدد بعد اعتماد الإجراء.
4. **قبول Testing ببياناته المستقلة:** حفظ مسودة وصورها قبل الحسابات، اعتماد والبيع مغلق، مطابقة المستند والمخزون والدفتر، تعديل/حذف آمنان، محاكاة فشل القيد، تكرار وتزامن الطلب، صلاحيات وروابط 403، Flutter، وتنزيل التقارير الثلاثة وفتحها في Excel/LibreOffice. التأكد من عدم تغيير حالة البيع أو المستندات التاريخية تلقائيًا. فحص التنزيل عبر Nginx/PHP-FPM فعليًا، بما يشمل إزالة الملف المؤقت إن كان X-Sendfile مفعّلًا.
5. **قرار Production لاحق مستقل:** بعد نجاح Testing وموافقة منفصلة، خطة احتياط وصور وحماية بيانات ونافذة نشر قصيرة وإصدار سابق محفوظ. لا تنفيذ Production في هذه المهمة.
6. **التراجع:** عند فشل التحقق، إيقاف الكتابات المتأثرة والعمال قبل تبديل الإصدار وإعادة بناء Cache/OPcache المتوافقين. لا `migrate:rollback` ولا حذف قيود أو استرجاع قاعدة فوق معاملات جديدة. إذا حدث اعتماد جديد، تحتفظ قاعدة البيانات بقيوده؛ الرجوع إلى كود قديم يعيد خلل الاعتماد الأصلي، لذلك يبقى الاعتماد/التصحيح متوقفًا حتى إصدار آمن. عند وجود فرق مالي تحفظ الأدلة وتراجع مصادره، ولا تنشأ تسوية تلقائية.

المراجعة لا تعتمد نتائج التقرير السابق بوصفها تصريح نشر؛ الاختبار الجديد كشف فجوة حقيقية كانت خارج تغطيته. التغييرات الجديدة لهذه المراجعة محصورة في هذا التقرير واختبار إثبات الخلل داخل `OwnerOpeningExperienceTest.php`، دون Commit أو Push أو Deploy.
