# تحسين إدخال فاتورة الشراء وتركيبات المنتج

تاريخ التنفيذ: 2026-11-13. تنفيذ محلي، Laravel 13.35.0 وPHP 8.5.12 وMySQL معزول وChrome فعلي.

## السبب المثبت والنتيجة

كان Backend يدعم إضافة ألوان ومقاسات للمنتج الموجود بالفعل عبر `SavePurchaseProductAction::execute`، مع قفل المنتج ومنع تكرار التركيبة والمحافظة على أسعار الأصناف الموجودة. المشكلة كانت في مسار الواجهة: البحث يعرض Variants، والنقر يضيف Variant واحدًا مباشرة؛ زر «خيارات إضافية» كان مرتبطًا بنتيجة البحث وبصلاحية `inventory.manage_catalog`، ثم يختفي بعد الاختيار. لم يكن جدول الفاتورة يقدم مدخلًا واضحًا للعودة إلى تركيبات المنتج.

أصبح اختيار المنتج يفتح جدول تركيباته الفعالة والمسموحة، مع اختيار عدة أسطر وكمية وتكلفة مستقلتين. يبقى داخل مجموعة المنتج في الفاتورة زر «الألوان والمقاسات / إضافة تركيبات». المستخدم المخول يستطيع فتح نموذج المنتج نفسه وتعريف لون أو مقاس من داخله، ثم مراجعة جدول حاصل ضرب الألوان والمقاسات قبل إضافته إلى الفاتورة. بقي زر «منتج جديد» للمنتج المختلف فعليًا.

أظهر اختبار Chrome أثناء التنفيذ نقص `size_id` في DTO القديم للكتالوج؛ كان الاسم متاحًا لكن مفتاح مطابقة المقاس غير متاح. أضيف المعرّف، وأثبتت إعادة تجربة المتصفح احتفاظ كل تركيبة بالكمية والتكلفة المدخلتين. أضيف اختبار استجابة يغطي ذلك.

التحقق هنا مثبت من الكود واختبارات HTTP والمتصفح على بيانات معزولة؛ لم نقرأ بيانات `app_store` لتحديد حالة منتج حقيقي أو صلاحيات مستخدم حقيقي.

## التنظيم المستفاد من المرجع

فُحص [المرجع](https://nabeih.github.io/Clothing-store/) فعليًا في Chrome بعرضي 1440 و390، بما فيه قسم «إدارة المشتريات». استفدنا من فصل بيانات الفاتورة عن أصنافها، وتجميع تركيبات المنتج، وإبراز ملخص المنتجات والقطع والإجمالي والمدفوع والمتبقي. التنفيذ الأصلي يستخدم ألوان التطبيق ومكوناته الحالية، مع ملخص جانبي على Desktop وأسطر قابلة للتحرير على Mobile.

لم يُنسخ كود أو شعار أو صور المرجع. لم يُنقل خيار خلط الافتتاح بالمشتريات أو منطق الحسابات التجريبي أو الحفظ التلقائي المحلي من المرجع؛ بقيت المسودة والاعتماد وخدمات المخزون والدفتر في appStore هي المرجع الوحيد.

لقطتا المرجع المحليتان: `storage/app/reports/purchase-reference-desktop.png` و`purchase-reference-mobile.png`، للمقارنة فقط.

## ما بقي من النظام الحالي

- `Product` واحد وVariants متعددة؛ لا خدمة إنشاء موازية ولا جدول جديد.
- إعادة استعمال `SavePurchaseProductAction`، وطلبات التحقق والصلاحيات ومسارات تعريف الألوان والمقاسات والصور الموجودة. لم يتغير هذا Action ضمن المهمة.
- اختيار منتج أو تعريف تركيبته أو حفظ المسودة لا يزيد المخزون ولا ينشئ مستحقات أو دفعة. الأثر يحصل عند اعتماد الشراء عبر المسار القائم.
- لا يعاد ضبط سعر بيع Variant موجود؛ سعر البيع في نافذة الإضافة يخص التركيبات الجديدة فقط. تكلفة السطر تخص هذه الفاتورة ولا تعيد كتابة تكلفة مستند تاريخي.
- المنتج والتركيبة الموجودة في الفاتورة لا يتكرران عند الإضافة ثانية؛ تعدّل كمية السطر الموجود من الجدول. تبقى قيود التفرد والأقفال السابقة على الخادم فعالة.
- الملخص يأخذ قيمه من `PurchaseInvoiceController::preview` وحساب الخادم الحالي، مع حقل `paid` إضافي للعرض؛ لا حساب مالي بـFloat داخل JavaScript.
- نقطة القراءة الجديدة `GET /purchases/products/{product}/variants?branch_id=...` تستخدم `VisibleProductsQuery` و`OperationContext`، وتحمل جميع الصفحات بدل الاكتفاء بأول 30 نتيجة بحث. تتطلب `purchases.view` و`sales.view_cost` ضمن مجموعة المسارات الحالية. إنشاء المنتج/التركيبات يحتاج أيضًا `purchases.manage` و`inventory.manage_catalog` وفق Form Request القائم.
- الكاشير دون صلاحية التكلفة يُرفض من جهة السيرفر؛ تعريف الألوان والمقاسات لا يصبح متاحًا بمجرد رؤية واجهة المشتريات.

ملاحظة البنية: النظام الحالي يتطلب `color_id` و`size_id` لكل Variant ولا يحتوي نوع منتج مستقلًا بلا خصائص أو مفاتيح nullable. المنتج الذي يستعمل تركيبة عامة واحدة يبقى قابلاً للاختيار كما هو، دون إجباره على تركيبات إضافية. لم نُنشئ ألوانًا أو مقاسات «عامة» تلقائيًا ولم نغيّر Schema لتمثيل حالة جديدة غير موجودة.

## كيف تجرب 3 ألوان ومقاسين

1. من «المشتريات والموردون ← فواتير الشراء ← فاتورة شراء جديدة»، أو `/purchases/create`، اختر المورد والفرع والتاريخ.
2. ابحث باسم المنتج أو كوده، ثم اضغط نتيجته. تظهر نافذة تركيباته الموجودة؛ اختيارها وإدخال الكمية والتكلفة ثم «إضافة المحدد للفاتورة» يكفي لشراء Variant موجود.
3. لإضافة تركيبات للمنتج نفسه، اضغط «إضافة لون أو مقاس لهذا المنتج». يمكنك العودة إليه لاحقًا من زر «الألوان والمقاسات / إضافة تركيبات» في مجموعة المنتج داخل الفاتورة.
4. اختر ثلاثة ألوان ومقاسين. في قوائم Desktop المتعددة استخدم Ctrl مع النقر للاحتفاظ بالاختيارات. إذا كان لون أو مقاس ناقصًا، استخدم «تعريف لون» أو «تعريف مقاس»، وأدخل الاسم والكود ودرجة اللون عند الحاجة، ثم «حفظ واختيار». هذه الأزرار تحتاج صلاحية إدارة الكتالوج.
5. يظهر جدول 6 تركيبات مع حالة كل منها: موجودة أو جديدة. أدخل كمية وتكلفة كل سطر، وسعر البيع للتركيبات الجديدة، ثم «حفظ وإضافة للفاتورة». لا يُنشأ Product ثانٍ.
6. راجع الأسطر، وعدّل أو احذف أي سطر قبل الحفظ. إذا سبق إضافة تركيبة فلن تتكرر؛ عدّل سطرها الموجود. اختر حساب الدفع وأدخل الدفعة، أو صفرًا للآجل، وراجع عدد القطع والإجمالي والمدفوع والمتبقي.
7. اضغط «حفظ ومراجعة المسودة». راجع صفحة المستند؛ المخزون لم يزد بعد. عند استلام البضاعة فعليًا اضغط «اعتماد واستلام البضاعة» ثم أكد الاعتماد؛ عندها فقط يسجل النظام المخزون والقيد والدفعة المحددة.

للتجربة دون أثر على المحل استخدم نسخة وقاعدة اختبار مستقلة. الاعتماد في التطبيق الفعلي إجراء تشغيلي حقيقي، وليس معاينة.

## حماية العمل السابق وحدود التسليم

فُحص Git قبل التنفيذ، ولم تُحذف أو تُستبدل التعديلات السابقة. تطابقت بصمات `FinanceContext` و`OpeningFinancialSupport` و`CorrectInventoryAction` واختبارات الصور و`HomeRouteTest` و`DataMigrationSeeder` و`config/database.php` مع بداية المهمة. لم تتغير إعدادات البيئة أو الاتصال.

لا اتصال بقاعدة `app_store` أو Testing أو Production، ولا معالجة صور أو بيانات عميل، ولا Migration أو Seeder أو إغلاق إعداد أو تفعيل بيع على قاعدة حقيقية. لا تعديل لخدمات الاعتماد أو قيود المشتريات أو التصحيح المالي. لا Commit أو Push أو Deploy. لا ترحيل أو تحديث صلاحيات مطلوب لتجربة هذا الكود بحساب مخول حاليًا.
