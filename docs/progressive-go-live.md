# استكمال التشغيل التدريجي وحماية تعديلات المستخدم

تاريخ الاستكمال: 2026-11-05. PHP 8.5.12، Laravel 13.35.0. التنفيذ محلي، والكتابة الاختبارية على قواعد MySQL معزولة فقط.

## نقطة التوقف وما وُجد

آخر Commit هو `9baeb02` بتاريخ 2026-11-02. بقيت خدمات ProgressiveOperation وProgressiveStockProof وشاشة الجاهزية وربط قنوات البيع والاختبارات ملفات محلية غير مثبتة. آخر نتيجة محفوظة كانت 12 اختبارًا فيها فشلان: قاعدة accepted كانت تطلب إقرار الجرد حتى عند غياب المجموعة الاختيارية، ومسار الهاتف افتقد import لـOperationContext. عولج السببان، ثم استُكملت الاختبارات والتوثيق.

وُجدت تعديلات أقدم لشجرة الحسابات والمصروفات والتقييم والصناديق، وملف ZIP محذوف عمدًا في حالة Git الحالية؛ حُفظت جميعها ولم يُستعد أو يُحذف أي ملف عبر Git. لا يمكن نسبة كل ملف غير مثبت إلى صاحبه أو تأريخ تعديله بدقة من Git وحده.

التغييرات الأحدث المؤكدة من الملفات وتوقيتها:

- `database/seeders/DataMigrationSeeder.php`: استيراد الفروع والمستخدمين والتصنيفات والمنتجات والصور والمخزون والحركات والجهات والمشتريات؛ تحويل القيم إلى الوحدات الصغرى، وفحوص تمنع إعادة الاستيراد بعد وجود حركات تشغيلية. يستثني جداول النظام من النقل. لم يُشغّل أو يُعاد تصميمه.
- `config/database.php`: اتصال إضافي بقاعدة النظام القديم `appstoredb`. لم يوجد ملف مستقل باسم config.php ضمن ملفات المشروع التي كشفها البحث. عومل database.php بوصفه الملف المحمي المقصود.
- `PrepareSetupTokenCommand.php`: تعليق جديد يوضح أمر تجهيز التوكن، و`public/.gitignore` ملف غير متتبع. حُفظا.

طالت أداة Pint أثناء الاستكمال الملفات الثلاثة الأولى تنسيقيًا رغم تمرير نطاق ملفات مع --dirty. أُعيدت نسخها الأصلية من سجل VS Code بعد مطابقة SHA-256 مع بصمات بداية الجلسة، دون استعادة من Git. `progressive-protected-final.json` يثبت تطابقها الحرفي النهائي. لم يتغير منطق الاستيراد أو الإعدادات ولم يُتصل بالمصدر القديم.

## ما تغير في التشغيل

كان `OperationContext::salesStarted` يمنع البيع بمجرد بقاء opening_stock_closed_at فارغًا. أصبح يستند إلى حالة الفرع:

| الحالة | السلوك |
|---|---|
| setup | الإعداد مفتوح ولا يوجد اعتماد تشغيل تدريجي؛ البيع ممنوع |
| progressive | اعتماد صريح من المالك؛ يسمح فقط بالمخزون المثبت والحسابات الجاهزة، مع بقاء إدخال افتتاح أصناف أخرى وفق الدليل |
| full | إغلاق الإعداد بالمسار القائم بعد اجتياز مطابقة الإنهاء؛ لا إعادة ترحيل مبيعات أو افتتاح |

لا جداول أو أعمدة أو Migrations جديدة لهذه المهمة. يُحفظ اعتماد التشغيل وتاريخ الانتقال ولقطة الجاهزية في AuditEvent قائم مرتبط بالفرع، تحت القفل والمعاملة المشتركة. لا فتح تلقائي أو إعادة تعيين لتاريخ الانتقال. الحسابات المركزية وتفعيل البنية القائمة للمبيعات والتوازن المالي تبقى شروطًا مشتركة لا يتجاوزها وضع الفرع.

أُعيد استخدام OperationContext وStockLedger وSaveSaleAction وPrepareSaleAction وPostSaleAction وReturnSaleAction وExchangeSaleAction وPostJournalAction وخدمات المشتريات والقبض والموقع والمزامنة. تقييم التكلفة الحالي متوسط تكلفة القيمة المتاحة موزعة على الكمية بواسطة Money::ratio؛ لم يُضف FIFO أو Lots ولم تُعدّل تكلفة بيع تاريخية.

## شاشة المالك وطريقة التجربة

الرابط المحلي: http://127.0.0.1:8000/inventory/operation

من «المنتجات والمخزون ← حالة تشغيل المحل»، يختار المالك الفرع، ويفحص الأصناف وحسابات القبض وأسباب المنع. الشاشة تعرض الحالة وتاريخ الانتقال وتحذير عدم اكتمال التقارير، وبحثًا وتصفية للأصناف ورابط إنهاء الإعداد.

1. استكمل التهيئة المركزية القائمة وصلاحيات المالك؛ الشاشة توضح نقصها. لم يُشغّل app:sales-setup في هذه المهمة.
2. راجع افتتاح الصنف ومستنده وحركاته وقيده المالي. قيمة inventory وحدها ليست إثباتًا.
3. اعتمد بداية حقيقية لحساب القبض من شاشة الحسابات، بما فيها صفر موثق؛ إنشاء حساب برصيد عرض صفر لا يكفي.
4. راجع الجهات: البيع النقدي العابر لا ينشئ ذمة؛ التعامل بدين يحتاج بداية معتمدة للجهة. اعتماد الصفر متاح فقط لجهة جديدة دون تاريخ مالي سابق.
5. حدّث الجاهزية، أدخل سبب التفعيل وأكد مراجعة المصادر والحركات الخارجية، ثم اضغط «بدء التشغيل التدريجي» بنفسك. يتغير التقرير فيرفض الاعتماد القديم حتى تحديثه.
6. جرّب الكاشير بصنف جاهز وحساب جاهز؛ إدخال صنف آخر يحتاج لقطة الجرد الأصلية قبل/عند الانتقال ودليلها، لا جرد اليوم على أنه افتتاح قديم.
7. بعد استكمال كل الأرصدة، استخدم إنهاء الإعداد القائم. يعاد الفحص وتُحفظ لقطة الاعتماد فقط؛ لا كميات أو قيود إضافية.

لم يُفعّل أي فرع في قاعدة المحل ولم تُغلق فترة إعدادها. توفر صفحة المعاينة لا يعني أن البيانات الحالية اجتازت الجاهزية.

## شروط الإثبات والحماية

لكل SKU: تطابق الكمية والقيمة مع الحركات، مصادر افتتاح/شراء/بيع/مرتجع معتمدة ذات ربط صحيح وقيد متوازن مطابق لحساب المخزون، وحالة المنتج والمتغير والتصنيف واللون والمقاس الفعالة. NULL تكلفة مجهولة، بينما صفر معروف يحتاج تأكيدًا ودليلًا مستقلين. المتاح يحترم الحجوزات. لا تُستعمل مشتريات لاحقة لتغطية افتتاح غير مثبت لصنف مختلط.

لحساب القبض/الصرف: حساب فعّال قابل للترحيل في الفرع، افتتاح مالي فعّال غير معكوس حتى لو صفرًا، وعدم وجود تاريخ سابق غير مغطى أو حركات من فرع آخر أو رصيد سالب. كل حسابات الدفع المقسم تُفحص.

الأثر المالي غير المرحل المحدد بمستند وصنف يمنع ذلك الصنف دون منع صنف مستقل مثبت. أي أثر مالي متبقٍ غير قابل للعزل أو حركة بلا رصيد مقابل يمنع الفرع حتى المراجعة. لم تُجرَ تسوية للفرق التاريخي 250 أو أي فرق لاحق، ولم تُعد قراءة أو اعتماد أرقام حالية من قاعدة المحل في هذا الاستكمال.

Seeder المستخدم ينقل قيم المخزون ومصادر قديمة ولا ينشئ بنفسه قيود إثبات مالي لكل هذه المصادر؛ وجودها بعد الاستيراد لا يجعلها جاهزة تلقائيًا. الحل الآمن هو مراجعة المصادر عبر المسارات المالية المعتمدة بعد موافقة مستقلة، لا تغيير الاستيراد أو فتح استثناء في البيع. لم يُختبر تنفيذ Seeder أو صحة البيانات القديمة.

يعاد الفحص داخل اعتماد البيع والمعاملة والقفل المشترك؛ تغيير الجاهزية بعد فتح الكاشير لا يسمح بالاعتماد. الموقع يفحص التسعير وتأكيد الحجز ثم التسليم عبر البيع القائم؛ الحجز لا يخرج البضاعة. فشل التسليم يعيد حتى تحرير الحجز. المرتجع يعتمد تكلفة الفاتورة الأصلية ويرفض غياب قيدها المثبت، والاستبدال يستخدم المسار الحالي دون إنشاء مسار بيع موازٍ.

الهاتف: `/api/v1/operation-state?branch_id=...` لصلاحية sales.sell ونطاق الفرع، دون تفاصيل التكلفة. sales_allowed أهلية عامة وليست شهادة صنف. تعاد جاهزية كل عملية Offline عند وصولها ولو لم تتغير نسخة المخزون. الرفض `conflict_requires_review/readiness_changed` يحفظ العملية للمراجعة دون أثر جزئي. تفاصيل العقد محدثة في flutter-api-contract.md وopenapi-flutter.yaml.

## الاختبارات والأدلة

- حزمة المبيعات والمخزون والمالية والتقارير والإعداد والموقع والمزامنة والتنقل: **128 اختبارًا، 1243 assertions ناجحة، صفر فشل أو تجاوز** في الجولة النهائية المحفوظة. تضمنت 15 حالة تشغيل تدريجي آنذاك.
- سباق MySQL مستقل بعمليتي PHP على آخر قطعة أثناء التشغيل التدريجي: **اختبار واحد، 8 assertions ناجحة**؛ بيع واحد وكمية صفر وقيود متوازنة. احتُفظ بقاعدته المعزولة للمراجعة، دون migrate أو حذف قاعدة.
- بعد إضافة اختبار الاستبدال، أُعيدت مجموعة التشغيل التدريجي كاملة: **16 اختبارًا، 159 assertions ناجحة**. أثبت اختبار الاستبدال الجديد منع الصنف البديل غير الجاهز مع التراجع عن المرتجع، ثم نجاح الاستبدال بعد استعادة جاهزيته، وعدم تكراره عند إعادة UUID. هذه المجموعة تتداخل مع الحزمة السابقة ولا تُجمع أعدادها معها.
- Chrome حي عبر HTTP على قاعدة `appstore_financial_audit_*` المعزولة بعرض1280 و390: الشاشة والحسابات والأصناف ظاهرة، دون تجاوز أفقي أو أخطاء JavaScript أو استجابات محلية فاشلة. حالة هذه العينة full؛ لم يُضغط زر اعتماد في المتصفح. حالات setup/progressive واعتماد الزر فُحصت باختبارات HTTP على MySQL.
- فُحص JavaScript وgit diff --check، وشُغّل Pint. لم تُعد الحزمة الكاملة لكل المشروع؛ لم يُشغّل Flutter فعلي أو Safari أو هاتف حقيقي.

الأدلة في storage/app/reports: progressive-regression-final.txt، progressive-final.txt (آخر إعادة للمجموعة المركزة)، progressive-mysql-race.txt، progressive-browser.json، progressive-readiness-1280.png، progressive-readiness-390.png، progressive-protected-before.json وprogressive-protected-final.json.

## ما بقي وحدود الاعتماد

الأرصدة القديمة غير الصفرية للعملاء والموردين تحتاج مسار انتقال موثقًا مستقلًا؛ لا يعتمد صفر يخفي تاريخًا. تصحيح افتتاح صنف تحرك بعد التشغيل، والجرد الفعلي المتأخر دون لقطة أصلية، وحركات مستوردة لا يثبت مصدرها المالي، ومرتجعات بيع قديم غير موثق، تبقى ممنوعة برسائل واضحة. بعض مصادر التصحيح غير المدعومة في إثبات التشغيل تتطلب مراجعة مصدر مستقلة؛ لا حلول محاسبية تلقائية.

اختبار انقطاع شبكة Flutter وعودتها على الجهاز الفعلي ينتظر المطورة وفق خطوات العقد المحدث. التدفق الخلفي نفسه مختبر على MySQL.

لا حاجة لموافقة لتغيير Seeder أو الاتصال لأنهما لم يُعدّلا نهائيًا. أي معالجة بيانات مستوردة، أو تفعيل وضع الفرع أو تهيئة مركزية أو إغلاق الإعداد، أو تطبيق ترحيلات سابقة معلقة، تحتاج مراجعة واعتماد منفصلين. لم يُنفذ migrate أو db:seed أو اتصال بالنظام القديم أو الإنتاج، ولم تتغير .env أو إعدادات الاتصال للاختبار؛ عزل العمليات جرى بمتغيرات العملية المؤقتة فقط. لم يحصل Commit أو Push أو Deploy.
