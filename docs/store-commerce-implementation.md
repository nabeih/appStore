# المتجر والطلبات والإشعارات والحد الأدنى للسعر
التاريخ: 2026-11-01. تنفيذ محلي؛ لا نشر ولا تهيئة لقاعدة app_store.

## ما نُفّذ
- متجر عام فعلي على /shop، يعتمد المنتجات المنشورة من قاعدة البيانات، مع الأقسام والبحث وفلاتر اللون والمقاس وصفحة المنتج وصوره وعينات القماش حسب اللون. سلة الضيف وإتمام الطلب ومعاينة السعر والرسوم محسوبة على السيرفر.
- هوية مرئية مستوحاة من مرجع التصميم: الأبيض والكحلي والبنفسجي والبطاقات والأقسام؛ لا استيراد لبيانات العرض الوهمية أو JavaScript التجريبي. اللوحة الداخلية تحتفظ بالتنقل والميزات القائمة، مع لوحة تحكم ببيانات فعلية، وجرس إشعارات وقائمة مستقلة لإدارة الموقع.
- قوائم وإضافة وتعديل إعدادات الموقع والمنتجات المنشورة والأقسام والبنرات والمناطق والعروض، مع إخفاء/تعطيل بدل حذف التاريخ. المنتجات المنشورة تشير إلى المنتجات القائمة؛ لا نسخ للمخزون.
- الطلبات نفسها متاحة في /store-orders و/site-admin/orders عبر Controller وActions موحدة، مع البحث والتصفية والترقيم وحالة التحصيل وسجل الإجراءات.
- المالك يحدد الحد الأدنى لكل Variant أو جميع تركيبات المنتج من /inventory/products/{product}/minimum. الكاشير يرى الحد الأدنى، ويؤكد التجاوز صراحة بعد جميع الخصومات. التكلفة والربح يظلان محميين بالصلاحيات القديمة.
- المخزون يعرض الإجمالي المحاسبي والمتاح والمحجوز، ويميز الحجز داخل المحل عن البضاعة الخارجة للتوصيل.

## دورة الطلب وسلامة الأثر
إنشاء الطلب لا ينشئ بيعًا أو قبضًا أو حجزًا. تأكيده يتطلب بدء التشغيل وفق الإعداد القائم، ثم يحجز الكمية بعد فحص المخزون والقيمة. إخراجه للتوصيل يحول الحجز إلى in_transit، ويمنع بيع هذه القطع في الكاشير.
عند التسليم تستخدم SaveSaleAction وPostSaleAction القائمتين مرة واحدة، وتحرر الحجز وتثبت البيع والقيود ضمن المعاملة نفسها. الفشل يعيد الفاتورة والحجز والمخزون والقيود والمصروف معًا.
الإلغاء قبل الخروج يحرر الحجز؛ بعد الخروج ينتظر تأكيد عودة البضاعة فعليًا. رفض الاستلام لا يبيع المنتجات ولا يحررها تلقائيًا. المرتجع بعد تسليم بيع معتمد يظل من وحدة مرتجعات المبيعات القائمة.

الكمية الخارجة غير المباعة تبقى ملكًا للمحل ضمن أصل المخزون؛ المتاح للبيع يستبعدها. الحجز لا ينشئ حركة StockLedger ولا يعيد تقييم المخزون. المتوسط يبقى وفق حوض التقييم القائم، وتثبت COGS عند البيع الفعلي؛ لم يُخترع تجميد تكلفة عند الحجز.

UUID وبصمة الطلب، وقفل عداد العمليات والفرع والطلب، وversion، والقيود الفريدة تمنع تكرار الأثر. إعادة UUID بمحتوى مختلف ترفض؛ إعادة الطلب المقبول تعيد نتيجته. معاينة Checkout موقعة ببصمة HMAC؛ تغيير السعر أو الرسوم بعدها يتطلب معاينة جديدة وموافقة العميل، ولا يغيّر اتفاقه بصمت.

## السياسة المالية المعتمدة
الإصدار: store_revenue_separate_provider_cost_v1.
رسوم العميل إيراد مستقل للمحل، وأجرة مزود التوصيل مصروف مستقل ومستحق مستقل. تحفظ السياسة والأسعار في Snapshot للطلب؛ تعديل الإعداد لاحقًا يخص الطلبات الجديدة ولا يعيد تصنيف القيود التاريخية.

| العملية | المدين | الدائن |
|---|---|---|
| إثبات رسوم التسليم/الرفض | ذمم العملاء | delivery_revenue |
| إثبات أجرة المزود | المصروف التشغيلي القائم | مستحقات المصروفات القائمة |
| قبض المنتجات نقدًا لدى المزود | courier_receivables | ذمم العميل عبر سند القبض القائم |
| قبض الرسوم لدى المزود | courier_receivables | ذمم العميل |
| قبض مباشر للمحل | حساب البنك/المحفظة/النقد المختار | ذمم العميل |
| توريد عهدة المزود | حساب المحل | courier_receivables |
| سداد أجرة المزود | مستحقات المصروفات | حساب المحل عبر سداد المصروف القائم |

لا مقاصة تلقائية بين العهدة وأجرة المزود. يورّد الإجمالي ثم تسدد الأجرة مستقلة؛ يمنع توريد أكثر من عهدته أو سداد أكثر من المصروف الفعلي. الحساب وطريقة الدفع والتحويل المؤكد تخضع للتحقق القائم.
رسوم رفض الاستلام هي رسوم المنطقة الأصلية حتى إذا شمل الطلب توصيلًا مجانيًا. صفر أجرة المزود المعتمد يختلف عن أجرة مجهولة؛ المجهول يمنع إخراج الطلب.
الأرصدة المعروضة تستند إلى الفاتورة وسندات القبض وتوزيعاتها والمصروف ودفعاته، بما فيها ما سُجل من الشاشات القديمة، وليست مجرد عدادات محفوظة في الطلب.
الربحية تضيف إيراد الرسوم إلى النتيجة التشغيلية وتطرح مصروف المزود ضمن المصروفات القائمة. مجمل ربح المنتجات يبقى خاصًا بالمنتجات؛ هامش النتيجة التشغيلية مقامه صافي المنتجات + إيراد الرسوم. لا تسمية «صافي الربح المحاسبي الشامل».

## الإشعارات والأمان
outbox دائم داخل معاملة العملية، ثم توزيع بعد Commit فقط؛ إعادة التوزيع لا تكرر إشعار المستخدم. الأمر app:alerts-dispatch يعالج الأحداث المعلقة، ومجدول كل دقيقة.
التحديث في المتصفح كل 30 ثانية مع تراجع عند الفشل وتوقف عند إخفاء الصفحة. الإشعارات وعداد الطلبات مقيدة بالمستخدم والصلاحية والفرع، وتختفي عند سحب الصلاحية. القراءة عبر POST وCSRF.
روابط إيصال الضيف واستعادة نتيجة UUID محصورة بجلسة صاحب الطلب، دون استعراض عام أو بيانات عميل في رسالة خطأ.
التجاوز محفوظ بتاريخ ومستخدم وكمية وسعر فعلي وحد أدنى وقت البيع، ويبلغ أصحاب صلاحية notifications.price_alerts. التأكيد لا يمنح sales.below_cost أو تجاوز الخصومات أو الأسعار؛ تلك القيود باقية.

## خطة التفعيل اللاحق — لم تُنفذ على app_store
1. موافقة منفصلة ونسخة احتياطية متسقة تشمل الملفات وTriggers وتجربة الاستعادة. مراجعة الحالة الفعلية والـpending migrations قبل التنفيذ.

3. تشغيل app:store-access --owner=<existing-owner> --confirm على الاتصال الصحيح بعد اعتماد التحديث؛ يمنح المالك فقط الصلاحيات الجديدة ويجهز الحسابين النظاميين دون أرصدة أو إغلاق إعداد.
4. تحديد فرع التنفيذ والسياسة ومناطق ورسوم التوصيل وأجرتي المزود عند التسليم والرفض، ثم الأقسام والمنتجات المنشورة والبنرات والعروض. لا يفتح المتجر قبل إتمام الإعداد المعتمد.
5. تشغيل Laravel Scheduler ومراجعة app:alerts-dispatch، HTTPS وAPP_URL وAPP_DEBUG=false والنسخ الاحتياطي. لا إرسال بريد/Push أو خدمات مدفوعة أضيفت هنا.
6. تجربة مشتركة مع Flutter وفق تحديث العقد، ثم تحقق تشغيلي مع صاحب المحل قبل نشر مستقل.
