# إصلاح البحث وتجهيز تكامل Flutter

التاريخ: 2026-11-01. PHP 8.5.12، Laravel 13.35.0، MySQL محلي. التغييرات محلية، دون Commit أو Push أو نشر.

## إصلاح الملاحظتين

### SA-01

كانت صلاحية رؤية المنتج المشترك لا تقيد المتغير الذي يطابق البحث أو المتغيرات المحملة معه. أضيف نطاق متغيرات في VisibleProductsQuery، ثم استُخدم في مطابقة البحث ومرشحات اللون والمقاس والترتيب وتحميل المتغيرات. الصور وعينات القماش تُحمّل فقط لألوان المتغيرات المسموحة للمنتج نفسه.

يشمل الإصلاح `/api/products` و`/api/products/{id}` و`/sales/catalog`، وكذلك تنقيح نتيجة حفظ/تعديل المنتج قبل إرسالها. في الكاشير يبقى النطاق هو الفرع المحدد، حتى للمالك؛ في واجهة الكتالوج العامة يستطيع المالك البحث في جميع فروعه ما لم يحدد فرعًا. المستخدم المحدود لا يوسع نطاقه بإرسال branch_id لفرع آخر.

تبقى صلاحية إدارة الكتالوج قادرة على رؤية المتغيرات غير المخزنة وفق سياسة الإعداد القائمة. لم تتغير صلاحيات التكلفة أو الحسابات أو منطق المخزون. بقي دليل العملاء المشترك D-01 كما هو؛ لم نضف ارتباطًا جديدًا بين العملاء والفروع.

الاختبارات تؤكد غياب SKU والمقاس واللون والصور وعينة القماش للمتغير الحصري لفرع آخر، وعدم ظهوره في نتائج البحث أو إجماليها، وسلامة رابط التفاصيل. وتؤكد بقاء البحث المحلي وقراءة المالك المشروعة متاحين. انعكاس عبارة بحث كتبها المستخدم بنفسه في روابط Pagination لا يُعد جلبًا لسجل محظور؛ التحقق يميز ذلك عن بيانات النتائج.

### SA-02

مرشح `valuation` خاص بمراجعة المخزون المعتمدة، التي تبني انضمام `history` وتحتاج صلاحيات التقييم والتكلفة. كانت SearchRequest تسمح به في البحث العام، حيث لا يوجد هذا الانضمام.

أصبحت SearchRequest ترفضه خارج `inventory.review.index` و`inventory.review.export`. طلب JSON غير صالح يعيد422 مع خطأ validation للمرشح، حتى مع Debug مفعل؛ لا يُنفذ الاستعلام الخاطئ ولا تُرسل تفاصيل SQL أو Trace. تبقى شاشة المراجعة وتصديرها تعملان بالمرشح `mismatch` والصلاحيات الحالية. لم نضف معالج أخطاء عامًا يبتلع أخطاء التطبيق الأخرى.

أُنشئ مالك وكاشير وفرع وتصنيف ولون ومقاس وعميل ومورد تجريبيون. استُخدم BootstrapOwnerAction وCompleteFirstBranchAction وapp:sales-setup، ثم اعتماد صفر حساب النقد وإنهاء إعداد **فرع التكامل وحده** عبر Actions القائمة بعد نجاح تقرير الجاهزية. لا إغلاق أو تغيير لفترة app_store.

الملف خاص وخارج public ومتجاهل من Git، وكلمة المرور مولدة عشوائيًا وليست مطبوعة هنا. لا ترسل هذا الملف مع المستودع أو تضعه في تطبيق Flutter المنشور. ملف `http-outbox.json` في المجلد نفسه يحفظ دفعة التجربة ومعرف جهازها، دون Bearer token، لتكرار الطلب نفسه دون اختراع UUID جديد.

## نتيجة HTTP الفعلية

شُغّل خادم اختبار منفصل على `http://127.0.0.1:8011` بمتغيرات اتصال قاعدة التكامل فقط. استُخدمت طلبات HTTP فعلية عبر loopback، وليس استدعاء Actions المزامنة مباشرة:

- دخول Bearer للمالك والكاشير، وخروج ناجح لكليهما.
- Bootstrap مجزأ إلى38 صفحة بحد سجلين لكل طلب، ثم Pull تدريجي بعد تعديل منتج.
- دفعة معكوسة الترتيب لإنشاء منتج ثم شراء4 قطع بتكلفة20 ثم بيع قطعة بسعر35 وقبض10؛ رتّبها السيرفر وفق التبعيات وقبل العمليات الثلاث.
- الرصيد الخاص بسيناريو التقرير:3 قطع، قيمة6000 بالوحدة الصغرى، وذمة بيع2500. إجمالي المدين والدائن في قاعدة التجربة29000 لكل طرف.
- طلب حالة العمليات بعد تجاهل الرد، ثم إعادة الدفعة المحفوظة من عملية PHP أخرى: `already_applied` للثلاث، دون زيادة المستندات أو حركات المخزون أو القيود.
- UUID نفسه مع محتوى مختلف: `conflict_requires_review`.
- كاشير لا يتلقى average_cost أو value_minor، وطلب المشتريات يُرفض403.

الأعداد عند فحص إعادة الدفعة: منتجان،فاتورتا شراء،فاتورتا بيع،4 حركات مخزون،7 قيود و16 سطر قيد؛ بقيت ثابتة بعد الإعادة. توجد تجربتان اصطناعيتان محفوظتان: توقف أول فحص خارجي عند قراءة due_minor كعمود بدل accessor، وتوقف التالي عند استعمال id بدل product_id في إيصال المنتج. صُححت مراجع الفحص، ولم يُغير كود الأعمال أو تُحذف النتائج؛ استكملنا التجربة الموثقة من Outbox المحفوظ ومعرفات العمليات الموجودة.

الانقطاع الذي اختُبر هو فشل اتصال بعنوان loopback غير مستمع، مع حفظ الدفعة وإعادة إرسالها، ومحاكاة ضياع الرد بتجاهله ثم طلب الحالة. **لم نطفئ Wi-Fi فعليًا ولم نشغّل Flutter أو SQLite على هاتف.** لا ادعاء بأن تجربة التطبيق أثناء الطيران أو إغلاقه بالقوة مكتملة.

## خطوات مطورة Flutter

استخدمي docs/flutter-api-contract.md وdocs/openapi-flutter.yaml، وBase URL المحلي:

`http://127.0.0.1:8011/api/v1`

1. **الاتصال الأول:** سجلي الدخول بحساب التجربة، واحفظي Token في مخزن آمن ومعرف الجهاز بصورة دائمة. نزلي /auth/me ثم Bootstrap مع استمرار Pull إلى has_more=false. احفظي كل صفحة وCursor في SQLite ضمن معاملة واحدة. قارني المنتج/المتغير/اللون/المقاس والصور بالاستجابات؛ الكاشير لا يرى حقول التكلفة.
2. **العمل دون اتصال:** فعلي وضع الطيران فعليًا. يجب أن تبقى القراءة من SQLite متاحة حسب سياسة التطبيق. أنشئي منتجًا ومتغيرًا بمعرفي Client UUID، ثم شراءً وبيعًا تجريبيين مع التبعيات. خزني Outbox وUUID وclient_created_at والمحتوى مرة واحدة؛ لا تعرضي العملية كمعتمدة مركزيًا أو تطبعي SKU نهائيًا قبل قبول السيرفر.
3. **إعادة تشغيل التطبيق وهو Offline:** أغلقي التطبيق بالقوة وافتحيه؛ يجب أن تبقى SQLite وOutbox والتبعيات سليمة، دون تسرب Cache حساب آخر. هذا لم يُختبر من جهة Backend وحده.
4. **عودة الاتصال:** استرجعي الصلاحيات والفرع، ثم أرسلي الدفعة نفسها إلى Push. اربطي النتائج حسب operation_uuid، وليس ترتيب المصفوفة. حدّثي ربط Client UUID بالمعرف وSKU النهائيين. لا تنشئي فاتورة جديدة لإصلاح timeout؛ اطلبي حالة العملية أو أعيدي UUID نفسه والمحتوى نفسه.
5. **ضياع الاستجابة:** اقطعي الشبكة بعد إرسال الطلب وقبل وصول الرد، ثم أعيدي تشغيل التطبيق والاتصال. المقبول مرة واحدة يرجع already_applied دون زيادة المخزون أو المبيعات أو القيود. لا تحذفي Outbox قبل حفظ الإيصال وربط المعرفات ذريًا.
6. **التعارض:** جهازان يبيعان آخر قطعة، أو تعديل منتج من الويب قبل مزامنة تعديل Offline. اعرضي conflict_requires_review؛ لا تبدلي UUID تلقائيًا ولا تنفذي last-write-wins. اختبارات التزامن Backend موجودة؛ واجهة مراجعة الرفض وتجربة جهازين فعليين تنتظر مطورة Flutter.
7. **الصلاحيات أثناء الانقطاع:** اختبري سحب صلاحية/تغيير فرع/إبطال الجهاز على السيرفر ثم العودة. عند تغير نطاق Cursor أعيدي Bootstrap حسب العقد، ولا تدمجي Cache القديم بالنطاق الجديد. اختبري401 و403 و409 و422 و429 و503 وحفظ المرفوضات دون فقدها.
8. **الصور:** ارفعي الصورة بعد قبول المنتج/اللون، وبمعرف عملية رفع ثابت عند الإعادة، وتحققي من نسختي WebP وعدم تكرار الملفات. اختبارات رفع السيرفر موجودة؛ الكاميرا واختيار الملف وCache الصور على Flutter لم تُختبر.
9. **معيار النجاح:** بعد الاستقرار يتطابق Flutter مع المخزون والفواتير والذمم المركزية، ويظل القيد متوازنًا، ولا يزيد عدد المستندات عند تكرار الدفعة. بعد بيع مثال4−1 تظهر3 قطع وذمة25.00؛ لا تجمعي تجربة سابقة ضمن توقع تجربة منفردة.

Android Emulator يحتاج عنوان المضيف مثل10.0.2.2 بدل loopback الجهاز، مع إعداد HTTP للتطوير فقط عند الحاجة. الهاتف الفعلي يحتاج وصول شبكة محلية آمنًا؛ الخادم الحالي يستمع على127.0.0.1 فقط، ولم يُعرض على LAN أو الإنترنت. لا تعدلي Base URL للإنتاج بغرض الاختبار.

## حماية app_store وما بقي

فحص نهائي للقراءة فقط أكد الاتصال local/mysql/127.0.0.1/app_store، وعدم وجود جداول mobile_* أو سجل لتنفيذ ترحيلي المزامنة عليها. لم نستخدم حساباتها أو بياناتها في الاختبارات، ولم نشغل عليها Migration أو Seeder أو تصحيحًا. لا ندعي ثبات بصمتها إن استمر المستخدم بإدخال بيانات من الواجهة أثناء العمل.

جاهزية Backend لهذه التجربة مثبتة ضمن الفحوص المذكورة. ينتظر مطورة Flutter: تنفيذ عميل SQLite/Outbox الفعلي واختباره على الأجهزة، انقطاع الشبكة الحقيقي وضياع الاستجابة، التخزين الآمن وواجهة التعارضات وأداء تحميل الصور. الإنتاج وaaPanel وتطبيق الترحيلات على app_store خارج التنفيذ الحالي.
