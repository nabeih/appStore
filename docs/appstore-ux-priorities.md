# أولويات تجربة صاحب المحل وحالة معالجتها

2026-11-10. مبني على المسارات وBlade وJavaScript والخدمات المحلية. **مثبت من الكود والاختبارات** لا يساوي تجربة Chrome أو اعتماد بيانات العميل؛ نتائج الجولة الموسعة في [تقرير التنفيذ](appstore-pricing-and-purchasing-review.md).

## موانع البدء، حسب التأثير

| الأولوية | العائق | الحالة الحالية | ماذا يفعل المالك/المطوّرة؟ |
|---|---|---|---|
| 1 | غياب التهيئة المركزية رغم إنشاء المالك والفرع | مسار مسؤول قائم، لا معالج Web جديد؛ لم يفعّل على قاعدة عميل | المطوّرة تتحقق من التهيئة والمالك والحسابات، ثم يستخدم المالك `/inventory/operation`. لا يشغّل أمرًا إداريًا على حساب مجهول |
| 2 | مخزون أو افتتاح قديم غير مثبت ماليًا | الحماية والتشخيص محفوظان؛ لا معالجة تاريخية تلقائية | `/inventory/readiness` ثم المستند المصدر، ومراجعة مستقلة للأدلة. لا إعادة استقبال OS أو تسوية أو إغلاق لتجاوز الفرق |
| 3 | درج برصيد صفر غير معتمد | الدليل يميز التعريف من اعتماد البداية، والفحص يعرض السبب | `/finance/accounts` ← اعتماد رصيد بداية قبل أول حركة؛ اعتماد الصفر فقط إذا كان حقيقيًا |
| 4 | ذمم قديمة غير صفرية تحتاج مسار انتقال | لا واجهة عامة جديدة لإدخالها؛ اعتماد الصفر ليس بديلًا | لا توقع شمول الذمم ولا تخلق فاتورة وهمية. التخطيط لنقل موثق منفصل؛ البيع النقدي العابر للجاهز لا يتطلب عميلًا جديدًا |
| 5 | الخلط بين المسودة والاعتماد والتشغيل وإنهاء الإعداد | الإصلاح السابق يجعل الاعتماد موحدًا؛ أضيف دليل خطوات ونتائج وأسباب منع | [اليوم الأول](appstore-owner-first-day.md): بضاعة ← حساب قبض ← جاهزية ← قرار تشغيل ← كاشير. لا يلزم الكامل لأول بيع في التدريجي |
| 6 | عدم إيجاد منتج الشراء أو تعذر اختيار خياراته | أصلحت مطابقة الكلمات والمسافات، واختيار منتج بلا Variants، ومسار الخيارات الذي كان يحتاج صلاحية افتتاح | `/purchases/create`: ابحث بالاسم/SKU، اختر الموجود، أو ألوان/مقاسات لنفس المنتج بموجب إدارة الكتالوج. لا مخزون عند حفظ المسودة |
| 7 | تجاوز الحد الأدنى كان تأكيد كاشير فقط | أصلح Backend المشترك؛ يحتاج تغيير السعر وسببًا وتأكيدًا. الحقول تظهر للمخوّل عند إنشاء التركيبات | الكاشير يعدل السلة أو يطلب مسؤولًا يعمل بحسابه. لا Token موافقة أو حساب عام متداول |
| 8 | ظهور روابط لا تملك كامل صلاحيات وجهتها | أصلحت روابط المشتريات والافتتاح من المخزون، والكاشير من الحسابات، والمراجعة من التشغيل | الروابط المحجوبة لا تمنح إذنًا ضمنيًا؛ حراس Routes وActions مستمرون. إذا احتجت ميزة، يراجع المالك الدور، لا يتم منحها آليًا |
| 9 | الخلط بين تسجيل مصروف ودفعه وتعريف حسابه | نصوص توضيحية وجدول استفادة وكشف فصل المصروف عن التدفق النقدي | `/finance/expenses`: مراجعة المسودة ثم الاعتماد ثم سند صرف. `/finance/chart` تعريف وتصنيف لا يغيّر ربط المصروف تلقائيًا |
| 10 | شهرية المصروف المدفوع مقدمًا غير ممثلة | أضيف مسار محلي وجدول واعتراف وتقرير؛ الترحيل على Sandbox فقط | لا تسجل إيجار سنة كله في شهر. اختر متعدد الأشهر بعد تجهيز النسخة المعتمدة، وراجع الحصص والمستحق والدفع الفعلي |

## مصطلحات يجب شرحها في العرض

| مصطلح النظام | الشرح لصاحب المحل |
|---|---|
| Variant / SKU | تركيبة منتج ولون ومقاس، لها رصيد وسعر |
| اعتماد الافتتاح | إثبات بضاعة البداية وحركتها وقيمتها في الدفتر، دون دين مورد |
| baseline / دليل قيمة | توثيق قيمة رصيد مؤهل؛ لا ينشئ قيدًا ماليًا ناقصًا |
| الجاهزية | فحص المصدر والكمية والقيمة والحساب والصلاحية؛ ليس وجود اسم المنتج فقط |
| التشغيل التدريجي | بيع الجاهز بعد قرار المالك مع بقاء استكمال البداية؛ تقارير جزئية |
| إنهاء الإعداد | إقرار شمول ومطابقة الأرصدة وقفل إعداد الفرع، لا تسوية فروق |
| ذمة | مبلغ مستحق لك على عميل أو عليك لمورد/مستفيد |
| مصروف معتمد | تكلفة أو أصل استفادة ومستحق مسجل؛ لا يعني أنه دُفع |
| مصروف مقدم | استفادة تمتد إلى أشهر؛ دفعها نقد مختلف عن استهلاكها الشهري |
| عكس موثق | قيد معاكس بتاريخ مسموح يحفظ التاريخ، لا مسح للسجل |

## المتبقي الواضح، دون إخفائه بحل شكلي

- لا معالج واجهة واحد يجهز المحل كاملًا؛ ما زال الانتقال بين البضاعة والحسابات والتشغيل والجاهزية مطلوبًا. المستندات توضح الطريق، ولم نضف زرًا يتجاوز المراجعة.
- قد تبدو كلمة «إنهاء الإعداد» دعوة لإغلاق مبكر؛ استعمل التدريجي إن كانت بقية البيانات غير مكتملة، ولا توقّع إقرارات لا تعرف صحتها.
- نافذة الاستيراد تحمل عنوان Excel/CSV بينما الأداة تقبل CSV؛ استخدم النموذج CSV. لم تضاف قراءة XLSX.
- تصنيف المخزون غير قسم الموقع؛ راجع `/site-admin/content/products` و`sections` لنشر المنتج وربطه. لا نشر تلقائي عند الإدخال.
- الجذر `/` يفتح المتجر بعد التثبيت؛ مدخل المالك `/login`. اسم العلامة الداخلية في Sidebar ما زال نصًا ثابتًا، لا وعد بتخصيص كامل.
- لا موافقة مسؤول عن بُعد لتجاوز السعر، ولا تعديل عقد مصروف جزئي بعد الاعتراف، ولا جرد مخزون دوري حر بعد بدء الحركات. تحتاج تصميمًا مستقلًا؛ الحماية الحالية تمنع الاختصارات غير الآمنة.

## خطة قبول عملية على Testing مستقلة

1. راجع حزمة الملفات المحلية والجديدة ولا تستبدل تعديلات VPS أو ملفات `storage` أو `.env`. لا Commit أو نشر ضمن هذه المهمة.
2. جهّز نسخة وMySQL مستقلتين، واتفق على موافقة الترحيل الجديد هناك فقط. لا مصادر Legacy أو بيانات عميل.
3. اختبر رحلة [Demo](appstore-demo-script.md) بمالك ثم كاشير ودور مخصص، وبشاشة Desktop وهاتف، مع Console وNetwork.
4. تحقق من مسودة الافتتاح واعتمادها والمطابقة، والسعر وحدوده، وبحث الشراء واختيار المنتج والخيارات والمسودة والاستلام، وعدم ظهور التكلفة لغير المخوّل.
5. للمصروفات: عرض الجدول قبل الاعتماد، دفعة فعلية واحدة، استحقاق الحصص، إعادة التشغيل، شهر مغلق، عكس كامل، وثبات المستندات القديمة. راجع Cron وهوية المعتمد ورفضه عند سحب الصلاحية.
6. افتح HTML وJSON وExcel للفترة والفرع نفسيهما. جهّز ZIP وXMLWriter في PHP-FPM؛ نجاح تنزيل اختباري في CLI لا يثبت إعداد Nginx أو Excel الحقيقي.
7. عند فشل مالي: أوقف الكتابات المتأثرة واحفظ الأدلة؛ لا Rollback مدمر للجدول أو تعديل قيد تاريخي أو رجوع إلى كود يفتح خلل الافتتاح القديم. إصدار Production يحتاج موافقة وخطة بيانات منفصلتين.

**جاهزية Testing** تعني تجربة مستقلة تحت المراجعة بعد نجاح الاختبارات، لا تشغيلًا تجاريًا ولا تصحيح فروق العميل. ما يحتاج بيانات فعلية أو Chrome أو سيرفر أو مطوّرة Flutter يظل موسومًا بذلك.
