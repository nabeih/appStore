# سيناريو عرض appStore بأمان

## نطاق العرض وحالته

هذا **سيناريو واجهة مقترح**، وليس سجل جلسة Chrome منفذة. السلوك الأساسي مثبت من الخدمات واختبارات MySQL المحلية؛ شكل الخطوات والتفاعل والتنزيل والطباعة يحتاج قبولًا بالمتصفح على نسخة مستقلة. لا تستخدم قاعدة `app_store` للتعلم، ولا أسماء مستخدميها أو ديونها أو صورها.

تجهّز المطوّرة مسبقًا نسخة Demo بقاعدة MySQL جديدة مستقلة وملفات/جلسات/تخزين منفصلة. مثال عنوان فقط: `http://127.0.0.1:8020`، بعد التأكد من عزله؛ لم يُشغّل خادم على هذا العنوان هنا. يمنع بدء العرض قبل إثبات اسم قاعدة Demo. تجهيز Schema ورمز Setup والتهيئة المركزية مسؤولية المطوّرة ضمن موافقة قاعدة Demo، وليس تشغيل Seeder الاستيراد القديم. لا تعرض كلمات المرور أو الرموز على الشاشة.

مرجع البداية: [دليل اليوم الأول](appstore-owner-first-day.md). مرجع الجاهزية: [ProgressiveOperation](../app/Actions/Inventory/ProgressiveOperation.php)، [SetupReadinessReport](../app/Actions/Inventory/SetupReadinessReport.php).

## بيانات العرض

| العنصر | البيانات |
|---|---|
| المحل/المالك | اسم عرض تختاره وبريد تملكه إن أردت تجربة البريد؛ كلمة مرور خاصة بهذه النسخة |
| الفرع | فرع العرض، فعّال، دون أي ديون سابقة |
| التصنيف واللون والمقاس | ملابس العرض؛ أسود بكود `BLK`؛ `M` بكود `M` |
| المنتج الأول | قميص العرض، كود `DEMO-SHIRT`، 10 قطع، تكلفة 20.00، بيع 35.00، حد أدنى 32.00 |
| المنتج الثاني | بنطال العرض، كود `DEMO-PANTS`، 5 قطع، تكلفة 30.00، بيع 50.00، حد أدنى 45.00 |
| الدرج | درج فرع العرض؛ بداية صفر حقيقي **معتمد صراحة** |
| الأطراف والمصاريف | لا مورد أو عميل معرف أو دين أو مصروف في المسار الأساسي؛ البيع نقدي عابر |

كل الأسماء أعلاه تجريبية. لا تفترض أن معرف الفرع أو الحساب أو المنتج يساوي 1؛ اختره من الشاشة.

## خطوات العرض الأساسي

### أ. المالك والفرع

1. افتح عنوان Demo ثم `/setup`، وأكمل نموذج المالك باستخدام الرمز الخاص بهذه النسخة. لا تعِد فتح Setup المكتمل.
2. من `/onboarding/branch` أدخل «فرع العرض»، ثم **حفظ الفرع والمتابعة**.
3. تتأكد المطوّرة من التجهيز المركزي القائم لهذه النسخة. إنشاء المالك والفرع لا يفعّل البيع. لا تنفّذ أمر التجهيز على نسخة العميل لتسريع العرض.

دليل التنفيذ: [BootstrapOwnerAction::execute](../app/Actions/Access/FirstRun/BootstrapOwnerAction.php)، [CompleteFirstBranchAction::execute](../app/Actions/Access/FirstRun/CompleteFirstBranchAction.php)، [SetupSalesCommand::handle](../app/Console/Commands/Sales/SetupSalesCommand.php).

### ب. إدخال المنتجين دون اعتماد

4. `/catalog/attributes`: أضف التصنيف واللون والمقاس المذكورين، أو أضفهم من داخل نافذة الافتتاح.
5. `/inventory/opening-stock` ← **إدخال بضاعة**: اختر الفرع وتاريخ اليوم، وأدخل المنتجين وقيمهما. **إضافة التركيبات للجدول** ثم راجع أن الإجمالي **15 قطعة بقيمة 350.00**.
6. اضغط **حفظ مسودة**. افتح المستند المحفوظ. اعرض للجمهور كلمة «مسودة»، ثم تحقق أن رصيد المخزون لم يرتفع وأنه لا قيد افتتاحي لهذا المستند. قد توجد تعريفات المنتجات بالفعل؛ هذه ليست كميات.

دليل التنفيذ: [PostOpeningStockAction::execute](../app/Actions/Inventory/OpeningStock/PostOpeningStockAction.php). الحفظ لا ينشر المنتجات بالمتجر العام.

### ج. الاعتماد والحساب

7. من صفحة المستند راجع الكميات والتكاليف، ثم **اعتماد المستند وإدخال البضاعة** مرة واحدة. افتح السجل نفسه ثانية، ولا تنشئ افتتاحًا جديدًا لاختبار التكرار.
8. `/inventory`: المتوقع 10 قمصان و5 بناطيل. `/finance/chart`: رصيد `inventory` **350.00 مدين** يقابله `opening_equity` **350.00 دائن**. لا ذمة مورد ولا دفعة ولا إيراد بيع.
9. `/finance/accounts`: اختر درج فرع العرض ثم **اعتماد رصيد بداية قبل أول حركة**، أدخل 0 وسببًا مثل «درج العرض فارغ قبل أول حركة»، أكّد واضغط **اعتماد الرصيد**. لا تنشئ درجًا ثانيًا إذا كان موجودًا من التجهيز المركزي.

دليل التنفيذ: [ManageOpeningDraftAction::approve](../app/Actions/Inventory/OpeningStock/ManageOpeningDraftAction.php)، [ManageFinancialAccountsAction::opening](../app/Actions/Finance/ManageFinancialAccountsAction.php).

### د. تشغيل الفرع دون إغلاق إدخال بقية البضاعة

10. `/inventory/operation?branch_id=<معرف الفرع>` ← **فحص جاهزية التشغيل**. يجب أن يكون الصنفان والدرج جاهزين، ولا مانع مركزي أو أثر مالي غير مفسر.
11. اكتب سبب العرض وأقر مراجعة الأصناف والحسابات والحركات خارج التطبيق، ثم **بدء التشغيل التدريجي**. هذا قرار تجريبي صريح داخل Demo فقط.
12. اعرض حالة «تشغيل تدريجي» واشرح: ما زال الإعداد مفتوحًا، لكن الصنف غير الجاهز لا يُباع. لا تجرّب تصحيح افتتاح معتمد بعد الانتقال؛ الخدمة تمنعه لحماية التاريخ.

إذا بقي زر البدء غير متاح، **توقف عند سبب المنع**: حساب بلا بداية معتمدة، مسودة، تعريف معطل أو تهيئة ناقصة. لا تحذف مستندًا أو تعدّل علم التفعيل في DB لتكملة العرض.

### هـ. أول بيع

13. `/sales/cashier`: اختر الفرع والقميص نفسه، لون أسود ومقاس M وكمية **1**، بلا خصم أو تغيير سعر.
14. **زبون نقدي**، **سداد كامل الآن**، حساب الدرج، مقبوض **35.00**. راجع ثم **تسليم البضاعة وإتمام البيع**.
15. افتح الفاتورة من `/sales` وتحقق من الحالة، ثم جرّب عرض الطباعة في Demo فقط.

دليل التنفيذ: [PrepareSaleAction::execute](../app/Actions/Sales/PrepareSaleAction.php)، [PostSaleAction::execute](../app/Actions/Sales/PostSaleAction.php). السلة ومسودة البيع ليستا حجزًا، والاعتماد يعيد الفحص.

## النتائج المتوقعة حسابيًا بعد البيع

على فرض أن نسخة Demo لا تحتوي أي معاملات أخرى:

| المؤشر | المتوقع |
|---|---:|
| القمصان / البناطيل | 9 / 5 |
| إجمالي القطع | 14 |
| قيمة المخزون ورصيد حسابه | 330.00 |
| رصيد الدرج | 35.00 |
| مبيعات الفترة | 35.00 |
| COGS | 20.00 |
| مجمل الربح الحسابي لهذه الفاتورة | 15.00 |
| ذمة العميل والمورد | صفر في هذا السيناريو |

راجع نفس الفرع واليوم في `/sales/reports` و`/finance/treasury` و`/finance/inventory-reconciliation`. أثناء التدريجي قد تحجب الواجهة اعتماد الربح بسبب تحذير البيانات الجزئية، رغم صحة الحساب الرياضي أعلاه. لا تعد الجمهور بظهور ربح نهائي؛ [FinanceReports::completeness](../app/Actions/Finance/FinanceReports.php) يعلّم الفرع التدريجي غير مكتمل.

**امتداد اختياري بعد العرض الأساسي، في Demo فقط:** إذا اجتازت جميع الأرصدة الفحص ولم تبق مسودات أو جهات أو حسابات غير معتمدة، افتح أسفل `/inventory/readiness` وأدخل تاريخ البدء والسبب والدليل وإقرارات المطابقة، ثم **اعتماد أرصدة البدء وإنهاء الإعداد**. اعرض التحول للكامل وراجع التقرير من جديد. لا تغلق الإعداد الحقيقي للعرض؛ ولا يضمن مجرد الضغط نجاح الفحص إذا أضفت معاملات أخرى أثناء التجربة.

## عروض إضافية مستقلة

- **بحث شراء:** من `/purchases/create` ابحث عن `DEMO-SHIRT` أو اسمه واختر Variant نفسه؛ أدخل كمية وتكلفة واحفظ مسودة. المخزون يبقى كما هو. اعتماد الشراء بعد اختيار مورد مؤهل وصلاحية ترحيل ينشئ استلامًا وذمة مورد؛ الدفع يحتاج رصيدًا فعليًا. لا تعتمد شراءً فقط لتسوية افتتاح سابق.
- **حد السعر:** ادخل بكاشير Demo بصلاحياته الافتراضية؛ يرى سعر البيع والحد الأدنى، ولا يرى التكلفة. حاول تخفيض السعر دون الحد: يرفض الخادم تأكيد الكاشير وحده. المسؤول المخوّل يعتمد بحسابه وسبب وتأكيد؛ لا حساب موافقة خفي أو Token يتجاوز الدور.
- **مصروف متعدد الأشهر:** بعد اعتماد ترحيله على Demo، افتح `/finance/expenses`، اختر متعدد الأشهر، ومبلغًا وفترة تبدأ اليوم أو لاحقًا وتاريخ إثبات لا يأتي بعدها. احفظ واعرض جدول الحصص قبل الاعتماد. الاعتماد يثبت الأصل والمستحق، والدفع سند مستقل، والحصص المستقبلية لا تُرحل الآن. لا تغيّر الساعة أو تنشئ قيدًا تاريخيًا على قاعدة عميل لمحاكاة Scheduler؛ اختبارات الساعة المنضبطة تغطي ذلك في MySQL المعزول.
- **المتجر وFlutter:** يؤجلان عن المسار الأساسي. النشر في قسم موقع مستقل عن تصنيف المخزون، والـCheckout يحتاج إعدادات وتوصيل وجاهزية. Backend الهاتف موجود، لكن نجاح اختبار الخادم ليس تجربة Flutter على هاتف أو Offline حقيقي.

## قائمة القبول قبل عرض تجاري

**يحتاج تجربة واجهة:** RTL وهاتف وDesktop، نتائج البحث والاختيار، حفظ المسودة واعتمادها، تحديث الحالات، إعادة فتح الفاتورة، Excel والطباعة، Console وNetwork، وتسجيل دخول كاشير مع إخفاء التكلفة.

**يحتاج فحص بيئة Demo:** PHP والتبعيات المثبتة، GD/WebP للصور، ZIP وXMLWriter لـExcel، Storage وصلاحيات الملفات، Scheduler للميزات الجديدة، وعزل كل اتصال وملف عن بيانات العميل. هذه ليست أوامر نشر أو ترحيل منفذة.

**لا تعتبر الحسابات المتوقعة أعلاه نتيجة متصفح فعلية في هذه المهمة.** نتائج الاختبارات التنفيذية وحدودها في [مراجعة التسعير والشراء](appstore-pricing-and-purchasing-review.md) و[تصميم المصروفات](appstore-prepaid-expenses-design.md).
