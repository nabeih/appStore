# مراجعة سلامة إصدار appStore قبل تجربة Testing

تاريخ بدء العمل: 2026-11-12؛ تحديث التقرير النهائي: 2026-11-13. النطاق: التغييرات المحلية الحالية للمصروفات متعددة الأشهر والتسعير والمشتريات والافتتاح والتصحيح وواجهات Inventory وFlutter، مع إصلاح تجهيز اختبارات الصور. لم تُراجع أرصدة العميل أو ملفات VPS، ولا تعني هذه المراجعة اعتماد Production.

## نقطة البداية وحفظ العمل الموجود

فُحص `git status` و`git diff` والملفات غير المتتبعة وسجل Commits، وقورنت بالتقارير الخمسة المطلوبة. كان HEAD عند `43bb361`، مع مجموعة كبيرة من التعديلات والملفات الجديدة من الأعمال السابقة. لم تُستبدل هذه الملفات من Git ولم تُحذف. وجود ملف Untracked لا يعني أنه زائد؛ خدمات المصروفات والترحيل والاختبارات والوثائق الجديدة جزء من حزمة الإصدار.

بقيت بصمات `HomeRouteTest.php` و`ProductImageProcessingTest.php` و`CorrectInventoryAction.php` و`OpeningFinancialSupport.php` و`DataMigrationSeeder.php` و`config/database.php` مطابقة لبداية هذه المهمة. لم يتغير مسار الاستيراد أو إعداد اتصال دائم. أُعيد تنسيق نهاية أسطر HomeRoute إلى بايتاتها الأصلية بعد أن طبّق Pint تنسيق LF فقط؛ لم يُسترجع الملف من Git.

## مراجعة البنية والدورة المحاسبية

- **الترحيل:** `2026_11_10_140358_add_prepaid_expense_schedule.php` يضيف `recognition_method=immediate` افتراضيًا، وجدولًا بربط FK يمنع حذف المصروف صاحب الجدول، وفهرس `due_date` ومفتاح فريد `(expense_id, month)`. لا تحويل للمبالغ التاريخية إلى حصص ولا تعديل للأرصدة. `down` يرفض حذف الحالة المالية تلقائيًا. لم يُشغّل ترحيل في هذه المهمة؛ Schema الاختبار كان مجهزًا سابقًا. إنشاء جداول Fixture الصور ليس Migration للتطبيق.
- **المصروف:** Draft يحفظ المستند والجدول فقط. Approval يثبت الأصل مقابل المستحق؛ Payment مستقل يخفّض المستحق والصندوق، ولا ينشأ دفع شهري. Recognition يحوّل الحصة المستحقة من الأصل إلى مصروف الفترة؛ المستقبل يبقى مجدولًا. إعادة UUID والاعتماد والاعتراف لا تضاعف الآثار. العكس الكامل بعد عكس الدفعات يسجل قيودًا عكسية ويحافظ على التاريخ، ولا يحذف الجدول. كل خدمة مالية تستخدم `OperationContext::run`، والقفل المشترك ثم صف المصروف/الحصص؛ فشل القيد أو Audit يتراجع ضمن المعاملة.
- **الدقة:** `ExpenseSchedule` يستخدم Brick BigInteger وكسور أيام الشهر وتوزيع بواقي الوحدات الصغرى، لا Float. تقرير المصروفات يستخدم القيود، ويجمع عبر `Money::integer/sum` مع رفض Overflow. الشهر الكامل له وزن ثابت، والجزئي نسبة أيامه؛ مجموع الحصص يساوي مبلغ المستند.
- **الحسابات:** `ManageFinancialAccountsAction::provision` يستخدم `firstOrCreate` للحسابات المفقودة دون تعديل الموجود أو صلاحياته أو إضافة مبالغ. حساب `prepaid_expenses` يُنشأ عند اعتماد مصروف مقدم جديد فقط، ويُرفض تعريف قائم غير صالح بدل إصلاحه صامتًا. تصنيف الحساب أصل؛ تعريف حساب في الشجرة لا يعيد توجيه قيود التصنيفات تلقائيًا.
- **الافتتاح والتصحيح:** بقي اعتماد الافتتاح مشتركًا في `ManageOpeningDraftAction::approve`، مع المخزون والحركة والقيد والحالة والتدقيق معًا. المسودة ليست مخزونًا. `CorrectInventoryAction` و`OpeningFinancialSupport` يحسبان فرق القيمة ويطابقان سلسلة القيود دون الاعتماد على تفعيل البيع؛ تعديل Web وInventory API يمران بالمسار نفسه. المستند التاريخي بلا دليل صالح يُمنع، ولا إعادة اعتماد للـOS-000001 إلىOS-000031. لم يتغير هذان الملفان في المهمة الحالية.
- **التقييم:** `StockLedger::cost/move` يعتمد القيمة الحالية والكمية مع حساب صحيح للنسبة ومتوسط متحرك؛ لم تُضف FIFO أو Lots أو إعادة احتساب لتكلفة مبيعات تاريخية.
- **الحد الأدنى:** القرار على السيرفر بعد خصم السطر وتوزيع خصم الفاتورة. تجاوز الحد يحتاج `sales.override_price` وتأكيدًا وسببًا؛ الكاشير الافتراضي لا يتجاوز بمجرد Checkbox. البيع دون التكلفة له إذن مستقل. تغيير الحد العالمي يحتاج إدارة الكتالوج مع مالك أو تفويض سعر يشمل جميع الفروع. DTO الكاشير يعرض حد البيع دون تكلفة.
- **الشراء:** البحث عبر `VisibleProductsQuery` والتفويض قبل قراءة تكلفة الفرع. المنتجات بلا Variants يمكن اختيارها، وإضافة الخيارات تستخدم المنتج القائم والقفل وقيود التركيبة/SKU. إنشاء الخيارات يتطلب إدارة الكتالوج والتكلفة بالإضافة للمشتريات؛ مسار الخيارات الجديد لا يشترط صلاحية تصحيح الافتتاح. لا كمية قبل اعتماد الشراء.
- **القنوات:** Flutter يعيد استعمال `PrepareSaleAction/PostSaleAction` والشراء والافتتاح القائمة، مع Revision وفحص الصلاحيات عند Push. Inventory API لا ينشئ رصيدًا اعتباطيًا بل يمر بتصحيح الافتتاح المحمي. لا عملية Expense جديدة في بروتوكول Flutter الحالي؛ المصروفات متعددة الأشهر تُدار من Web وScheduler، فلا تُعرض كتطبيق هاتف منفذ.

المراجع الأساسية: `app/Actions/Finance/Expenses/*`، `app/Actions/Inventory/OpeningStock/*`، `app/Actions/Inventory/Setup/CorrectInventoryAction.php`، `app/Actions/Sales/PrepareSaleAction.php`، `app/Actions/Mobile/ApplyMobileOperation.php`، `app/Actions/Purchases/SavePurchaseProductAction.php`، و[دليل اليوم الأول](appstore-owner-first-day.md).

التجاوزات الفعلية السبعة:6 حالات `VisualRuntimeIntegrationTest` تحتاج نموذجًا وصورًا حقيقية، وحالة `GoLiveSchemaTest` المخصصة لنسخة Snapshot. لا فشل مخفي بين هذه التجاوزات. اختبارات `LegacyImageRecoveryCommandTest` الثمانية نجحت بعد عزل تجهيزها، بما فيها في الجولة الموسعة.

## التوافق وحدود التحقق

المثبت محليًا: Laravel13.35.0، Sanctum4.3.3، PHPUnit12.5.38، Pint1.32.1، PHP8.5.12. composer الخاص بالـframework وPHPUnit يسمح بـPHP8.3؛ يلزم تثبيت متطلبات الإصدار الفعلية في FPM، ولا نثبت حالة سيرفر لم نتصل به. ZIP غير مفعّل افتراضيًا في CLI المحلي؛ فُعّل للعملية الاختبارية فقط بـ`-d extension=zip` دون تغيير php.ini. XMLWriter وGD وPDO MySQL متاحة محليًا. يرفض Excel غياب ZIP/XMLWriter برسالة واضحة؛ الاختبارات تفحص XLSX وXML والصلاحيات وإبقاء النصوص الشبيهة بالمعادلات نصًا.

نجح اختبار التوزيع أيضًا على PHP8.3.16:3 اختبارات و6 Assertions، مع Syntax للملفات الستة المعدلة حينها، ثم Syntax لحارس الدقة. نجحت عليه كذلك حالات HTTP النهائية الست؛ لم تُعد حزمة MySQL كاملة على8.3. ظهر تحذير بدء واحد بأن ZIP محمّل أصلًا فيPHP8.3 بسبب إضافة خيار تفعيله للعملية؛ لم يمنع الاختبارات، ولا يحتاج تغييرphp.ini. فحص PHP8.5 شمل58 ملف PHP معدلًا أو جديدًا باستثناء Blade، وفُحص JavaScript بـ`node --check` للملفين المعدلين. نجح Pint و`git diff --check`.

لم يُنفذ Chrome أو Excel المكتبي أو Linux/PHP-FPM أو Cron حي أو هاتف Flutter أو فحص Testing/Production في هذه المراجعة. اختبارات الخادم لا تثبت UX الهاتف أو Scheduler الحقيقي. لا اتصال ببيانات العميل، ولا مطابقة بصمات لجداوله لأن قراءتها خارج النطاق؛ حماية العمل هنا مبنية على حصر الاتصالات وعدم تشغيل أوامر عليها، لا ادعاء مقارنة بيانات لم تُفحص.

## المتبقي والقرار

- **Critical:** لا يبقى خلل مالي مثبت غير معالج ضمن المسارات المختبرة. أُصلح اقتطاع الكسور، وأُثبت رفضه مع بقاء النصوص العشرية صحيحة؛ لا يعني ذلك تدقيق كل مسارات المشروع أو صحة أرصدة العميل.
- **High تشغيلي:** قبول Linux/FPM وExtensions وCron وصلاحيات المعتمد وهاتف Flutter غير منفذ؛ نجاح المحلي لا يكفي للنشر التجاري. أعمال العميل التاريخية وفروق المخزون خارج هذه المراجعة، ولا يجوز تشغيله اعتمادًا على عينات الاختبار.
- **Medium:** عقد المصروف المعتمد الجزئي/الاسترداد الجزئي ليس مسارًا منفذًا؛ يلزم نطاق مستقل بدل قيود مرتجلة. لا واجهة جديدة للتهيئة المركزية أو ذمم بداية غير صفرية. الملفات Untracked تحتاج إدراجًا ومراجعة في حزمة الإصدار لاحقًا حتى لا تُفقد عند النشر.

**القرار: جاهز لتجربة قبول Testing المعزولة، وليس لاعتماد Production.** الخطوة التالية فقط، بعد موافقتك: تنفيذ خطة القبول على قاعدة Testing مستقلة مع فحص البيئة والترحيل المعلق أولًا؛ لا تطبيق على العميل أو Production. لم يُنفذ Commit أو Push أو Deploy، أو ترحيل جديد أو استيراد أو تفعيل بيع/إغلاق إعداد/منح صلاحيات لمستخدم حقيقي.
