# إصلاح مانعي جاهزية تصحيح البضاعة الافتتاحية

التاريخ: 2026-11-10. **النتيجة: المانعان المثبتان عولجا؛ جاهز لتجربة Testing مستقلة ضمن هذا النطاق، وليس تصريح نشر Production.** لا خلل محاسبي مثبت متبقٍ ضمن مسار التصحيح المختبر.

## السبب والإصلاح

كان `CorrectInventoryAction` يغيّر كمية وقيمة البضاعة وحركتها ومستندها، ثم يسجل قيد الفرق فقط عند تفعيل البيع. أصبح تسجيل `opening_correction` مستقلًا عن `sales_controls.activated_at`، بعد إثبات المصدر المالي وقبل اكتمال Transaction.

أضيف `OpeningFinancialSupport` للتحقق من المستند المعتمد وسطوره ومجاميعه، والقيد الافتتاحي الصحيح: الفرع والتاريخ والحسابان النظاميان وإشارات المدين والدائن وعدم وجود عكس أو أطراف مورد/عميل. يشمل الفحص التصحيحات السابقة وقيمها الموثقة وقيود فروقها؛ فوجود رأس قيد وحده لا يكفي. يسمح بتصحيح قديم بلا قيد فرق فقط عندما يكون أثره القيمي صفرًا ومثبتًا، ولا ينشئ له قيدًا تلقائيًا.

تُرفض القيم المجهولة، وعدم تطابق قيمة الرصيد مع السطر والحركة، والقيد المفقود أو المعكوس أو المخالف، برسالة تطلب مراجعة المصدر والانتقال المالي. لا تنشأ قيود تاريخية ولا يعاد اعتماد مستند أو استقبال كمية تلقائيًا. لا تُسوّى فروق أخرى في بيانات المحل.

تعديل/حذف المخزون، وتصحيح الحركة والسطر ومجاميع المستند، وسجل `InventorySetupChange` التدقيقي، وقيد الفرق كلها في Transaction واحدة مع القفل المشترك وأقفال الصفوف وفحص `InventoryState::revision`. يلزم مستخدم مخوّل صراحة. تحفظ الحماية من الفرع الأجنبي والتصحيح بعد الحركات اللاحقة أو بدء التشغيل التدريجي أو إغلاق الإعداد.

الحساب بدقة الوحدات الصغرى دون float، باستعمال `Money` القائم:

- القيمة الجديدة = الكمية الجديدة × تكلفة الوحدة، ضمن سياسة الافتتاح الحالية وبشرط عدم وجود حركات لاحقة.
- فرق القيمة = القيمة الجديدة − القيمة السابقة الموثقة.
- عند الحذف: القيمة الجديدة صفر، والقيد يعكس قيمة السطر المحذوف فقط.
- تغيير السعر أو الهوية دون تغيير القيمة لا يغيّر رصيد المخزون المالي.

القيد بين `inventory` و`opening_equity` فقط؛ لا ذمة مورد أو فاتورة شراء. لا تغيير لطريقة تقييم المخزون ولا تكلفة مبيعات سابقة. القيد الافتتاحي الأصلي يبقى كما هو؛ التصحيحات قيود مستقلة.

تستخدم واجهة Web وخدمة Inventory API مسار التصحيح نفسه عبر `CorrectInventoryAction` و`UpsertInventoryAction`. عُدّل فحص `ProgressiveStockProof` ليثبت المستند المصحح من مجموع الأثر الأصلي والتصحيحات الصحيحة، مع مشاركة نتيجة الفحص لكل مستند داخل الطلب؛ لا Cache بين الطلبات أو قبول لفحص قديم عند الاعتماد.

المانع الثاني كان تجهيز اختبارات `InventorySetupTest` دون مستخدم اعتماد، ما يترك المستند مسودة بدل إنشاء Inventory. حُدّثت الاستدعاءات الثلاثة عشر لتمرير معرف المستخدم المسجل المخوّل صراحة؛ بقيت توقعات الاختبارات القديمة وضوابط المصادقة كما هي.

## نتائج التنفيذ الفعلية

الحالات الجديدة تغطي البيع المفتوح والمغلق؛ تغيير الكمية والتكلفة معًا وكلًا منهما منفصلًا؛ التصحيحات المتتابعة؛ الحذف الجزئي والأخير؛ المطابقة المالية بعد كل تصحيح ناجح في العينات المعزولة؛ ثبات القيد الأصلي؛ رفض رأس قيد غير مدعوم بمبالغ صحيحة أو بحساب/فرع/تاريخ صحيح؛ عكس القيد الأصلي أو قيد تصحيح سابق؛ فقد قيد تصحيح أو قيمة الرصيد؛ القيم الصفرية الصريحة؛ السعر وحده؛ إعادة الطلب القديم أو الطلب غير المتغير؛ ورفض غياب المستخدم.

حُقن فشل بعد إدخال سطر مالي بالفعل، في التعديل والحذف وحالتي البيع؛ تطابقت بصمات 12 جدولًا قبل الطلب وبعد التراجع، بما فيها المخزون والمنتجات والمتغيرات والحركات والمستند وسجله والقيود. اختبارات التدقيق القديمة أثبتت التراجع عند فشل كتابة سجل التصحيح كذلك.

سباقات تعديل/تعديل وحذف/حذف وتعديل/حذف تقبل عملية واحدة فقط للإصدار نفسه، مع سجل تصحيح وقيد فرق واحد، ودون حركة مخزون إضافية أو تغيير رصيد الصندوق. بقي مخزون العينة مطابقًا لحساب المخزون، وبقي البيع مغلقًا في السباق.

Pint وPHP lint و`git diff --check` ناجحة. الاختبارات الأساسية على PHP 8.5.12 وLaravel 13.35.0 المثبتين. فُحص Syntax للخدمة الجديدة على PHP 8.3 أيضًا؛ لم تُعد الحزمة كاملة على الإصدارين.

## حدود الجاهزية والخطوة التالية

لم تُشغّل حزمة المشروع الكاملة أو كل سيناريوهات التزامن خارج النطاق. لم يُختبر Chrome أو Linux/PHP-FPM أو Excel الفعلي في هذه المهمة، ولم تُراجع بيانات العميل أو تُعالج فروقها. احتُفظ بقيود ما بعد بدء الحركة والتشغيل التدريجي؛ لم يُضف مسار لتصحيح تكلفة مبيعات سابقة أو استرداد مستند مالي معكوس تلقائيًا.

الخطوة التالية تجربة Testing معزولة وفق خطة المراجعة السابقة: فحص البيئة وZIP/XMLWriter لتنزيل Excel، ثم تجربة المستخدم والتعديل والحذف والفشل وإعادة الطلب والتحقق من المطابقة على بيانات Testing فقط. لا ترحيل أو Seeder أو تحديث صلاحيات جديد مطلوب لهذه الإصلاحات. لم يُنفذ Commit أو Push أو Deploy أو تفعيل تشغيل أو إغلاق إعداد.
