# تحسين تجربة إدخال البضاعة ومراجعة التشغيل

تاريخ التحقق: 2026-11-09. تنفيذ محلي على Laravel 13.35 وPHP 8.5.12. لا نشر ولا تغيير لبيانات العميل.

## خلل اعتماد البضاعة

ثبت من الكود أن `PostOpeningStockAction` كان يضيف المخزون والحركات عند الاعتماد المباشر، لكنه يستدعي `PostJournalAction` فقط إذا كانت `sales_controls.activated_at` مفعلة. لذلك كان إغلاق البيع يسمح بإضافة المخزون دون القيد المالي، بخلاف مسار اعتماد المسودة.

أصبح الطلب المباشر يحفظ مسودة أولًا، ثم يستخدم `ManageOpeningDraftAction::approve` نفسه. اعتماد المستند وإضافة المخزون وحركته وتسجيل القيد والتدقيق كلها ضمن Transaction مقفلة واحدة. حفظ المسودة مستقل لكي تبقى الأصناف والتكاليف والصور إذا فشل الاعتماد المالي. عند فشل إنشاء المسودة نفسها تتراجع بياناتها وتنظف ملفاتها الجديدة وفق المسار القائم.

القيد الافتتاحي مدين على `inventory` ودائن على `opening_equity`؛ لا تنشأ فاتورة شراء أو ذمة مورد. يستعمل الاعتماد `ManageFinancialAccountsAction::provision` الموجود لإنشاء الحسابات النظامية الناقصة فقط. لا يغيّر الأدوار أو أرصدة حسابات القبض أو حالة البيع. الحساب النظامي المعطل أو غير القابل للترحيل يمنع الاعتماد، ولا يعاد تفعيله تلقائيًا.

لا تزيد كمية المخزون عند حفظ المسودة. التكلفة المفقودة مرفوضة ولا تستبدل بصفر أو سعر البيع. يعاد التحقق عند الاعتماد، بما يشمل مطابقة مجاميع المستند وتكاليف سطوره. وجود قيد سابق لمسودة يمنع اعتمادها ويطلب مراجعتها.

المستند المعتمد يعاد دون إضافة أثر جديد عند تكرار الطلب. المسودة الموجودة، خصوصًا إذا عُدلت، تحتاج فتح صفحتها واعتماد إصدارها الحالي؛ إعادة إرسال الطلب الأصلي لا تعتمدها ضمنيًا. الأقفال وفحص الإصدار يحميان الاعتماد المتزامن.

## تجربة صاحب المحل

- حفظ البضاعة كمسودة قبل تجهيز الحسابات، مع بقاء الصور والكميات والتكاليف.
- عنوان «جاهزة للاعتماد» عند اجتياز الفحص، و«مسودة» مع أسباب المنع عند تعذره، ورسالة «تم اعتماد البضاعة» بعد النجاح.
- التفاصيل الفنية داخل «تفاصيل للمسؤول»، مع إعادة الفحص على الخادم عند الضغط على الاعتماد.
- لا تشغيل تدريجي تلقائي، ولا فتح للكاشير، ولا إغلاق للفترة الافتتاحية.

## سبب رابط 403

ثبت عدم تطابق الشروط: رابط صفحة الجاهزية كان ظاهرًا دون شرط، والقائمة كانت تفحص `inventory.close_setup` و`sales.view_cost`، بينما Controller كان يشترط أيضًا `sales_owner` الفعال. لذلك ظهور الرابط لم يكن دليلًا على أهلية دخوله.

أضيف predicate مشترك `AccessPermissions::canViewOperation` وGate باسم `inventory.operation.view`، يستخدمهما الرابط والقائمة وController. بقي Middleware الصلاحيتين ونطاق الفروع قائمًا. هذا Gate مشتق من الصلاحيات الحالية؛ ليس صلاحية جديدة تُمنح للمستخدمين.

اختبرت دخول المالك المخول ورفض المدير حتى مع امتلاك الصلاحيتين، ورفض المالك عند فقد صلاحية مطلوبة وإخفاء الرابط عنه. لم أفحص حساب العميل أو أعدل بيانات صلاحياته؛ إذا بقي 403 لحساب المالك الحقيقي، يلزم التحقق من تفعيله ودوره والصلاحيتين وفرعه للقراءة فقط، ثم اعتماد أي تصحيح بيانات منفصلًا.

## تنزيل Excel

أصبحت التنزيلات العادية من التقارير الثلاثة ملفات `.xlsx` فعلية:

- `/inventory/readiness/export`: تقرير جاهزية المخزون وأدلة مصادره، بجميع النتائج المطابقة للبحث والفلاتر ونطاق الفرع، دون الاقتصار على الصفحة الحالية.
- `/inventory/readiness/export?setup=1&branch_id=...`: أرصدة ومطابقة الإعداد للفرع كاملًا، كما كان نطاق التقرير سابقًا؛ فلاتر الأصناف لا تغيّر معنى مطابقة حسابات الفرع.
- `/finance/transition?export=1`: كشف الانتقال المالي، مع دعم `branch_id` ضمن الفروع المسموحة.

تبقى JSON متاحة عند `Accept: application/json` أو `format=json`. لم تتغير صلاحيات التكلفة أو التصدير.

الأوراق RTL وعناوينها عربية. الكميات والمبالغ أرقام فعلية؛ القيم المجهولة خلايا فارغة، والأكواد وSKU نصوص تحفظ الأصفار الأولى. النصوص تستخدم inline strings ولا تنشأ Formula حتى عندما تبدأ بـ`=` أو `+` أو `-` أو `@`. تشمل أوراق الأرصدة المشتريات والدفعات والذمم والأدلة وموانع الإنهاء. بعض التفاصيل التقنية المركبة محفوظة كنص داخل ورقة مراجعة مستقلة.

لم تضف Composer Dependency. الكاتب يستخدم OpenXML عبر امتدادي PHP `ZipArchive` و`XMLWriter`، مع ملفات مؤقتة خاصة وتنظيفها بعد التنزيل أو الفشل. **يلزم تفعيل ZIP وXMLWriter في PHP الذي يخدم الموقع، وإتاحة الكتابة في مجلد الملفات المؤقتة.** ZIP غير مفعل في إعداد CLI الافتراضي المحلي؛ اختُبر باستخدام `-d extension=zip` للعملية فقط. لم أغيّر `php.ini` أو إعدادات أي سيرفر. عند غياب الامتداد يعاد رفض واضح بدل إنشاء ملف تالف.

## حماية التاريخ والبيانات

لا ترحيلات أو Seeders أو تشغيل لـ`DataMigrationSeeder` أو استيراد أو اتصال بـTesting/Production. لم تُعالج فروق المخزون والدفتر ولم تُنشأ قيود على قاعدة العميل. جميع الكتابات الاختبارية على MySQL معزول.

المستند المعتمد القديم الذي يفتقد قيدًا لا يعاد اعتماده ولا تستقبل كمياته مرة ثانية. يبقى ظاهرًا في «مراجعة الانتقال المالي» للمراجعة المنفصلة. لا يقرر هذا التنفيذ أن بيانات قاعدة معينة تدريبية أو حقيقية؛ لم يُجر مسح مستندات العميل أو إصلاح تاريخي لها. مسار معاينة الأثر المالي الحالي محفوظ دون استدعاء ترحيله تلقائيًا.

حُفظت تعديلات المستخدم السابقة في `tests/Feature/Catalog/ProductImageProcessingTest.php` و`tests/Feature/Auth/HomeRouteTest.php`؛ تطابقت بصمتاهما قبل التنسيق وبعده.

## التحقق وحدوده

إعادة التحقق المركزة نجحت: **73 اختبارًا و548 assertions**، تشمل إصلاحات المسودة والتصدير والمبيعات والانتقال المالي والتكامل المالي والصور الجديدة. الأدلة: `storage/app/reports/owner-experience-final-recheck.txt`.

الجولة الموسعة النهائية نجحت: **120 اختبارًا ناجحًا و1181 assertions**، مع اختبار تزامن اختياري واحد متجاوز لعدم تفعيل علمه في تلك الجولة (121 حالة إجمالًا). شملت إدخال البضاعة والجاهزية وإنهاء الإعداد والتنقل والتشغيل التدريجي ومزامنة Flutter والمتجر والمبيعات والمالية وحماية التقارير. الدليل: `storage/app/reports/owner-experience-verified.txt`.

ثم فُعّل اختبار التزامن صراحة وأعيد مع اختبارات Excel بعد آخر تحسين لبنية الملف: **5 اختبارات و74 assertions ناجحة دون تجاوز**. أعاد طلبا الاعتماد بعمليتي PHP المستند نفسه، مع حركة واحدة وقيد واحد وكمية واحدة وتدقيق اعتماد واحد. تُنسخ تعريفات الجداول إلى قاعدة MySQL جديدة معزولة دون تشغيل Migration؛ تبقى قاعدة السباق للمراجعة دون حذف. الدليل: `storage/app/reports/owner-experience-excel-race-final.txt`. هذه الجولات تتداخل، فلا تجمع أعدادها بوصفها اختبارات مختلفة.

الجولة الموسعة السابقة شغلت 120 اختبارًا وكشفت حالة إعادة طلب لمسودة كانت تتجاوز مراجعتها. أُصلحت بالحفاظ على رفض إعادة اعتماد المسودة من المسار المباشر، ثم أعيد اختبار الحالة ضمن الجولة المركزة. سجل الجولة السابقة محفوظ في `owner-experience-regression-final.txt` ولا يمثل النتيجة النهائية.

قياس SELECT بعد الإصلاح: 73 لأول اعتماد مع تجهيز الحسابات الناقصة، ثم 45 لصف واحد و45 لثلاثين صفًا. اختبار الأداء يفصل تكلفة التجهيز الأولى عن الطلبات التالية ويحتفظ بفحص عدم نمو العدد مع الصفوف، مع حد مستقل لقراءات حماية التثبيت. الأدلة: `owner-opening-query-profile.jsonl`. الارتفاع مقارنة بالمسار القديم مرتبط بحفظ المسودة والاعتماد المالي الإلزامي، وليس رفع حد لإبقاء الاعتماد الناقص.

Pint وPHP lint و`git diff --check` نجحت. لم تُشغّل الحزمة الكاملة للمشروع، ولم يُفتح الناتج في برنامج Microsoft Excel/LibreOffice فعليًا؛ اختُبرت سلامة ZIP وXML ومحتوى الخلايا وأنواعها عبر HTTP Feature Tests. لم يُختبر VPS أو Linux فعلي ضمن هذه المهمة، ولم يُغير إعداد السيرفر.
